# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A client-side Fabric mod for Minecraft that fixes vanilla bugs where the fishing line starts in the wrong place. In first person the line origin is placed on the rod the hand pass actually draws, at vanilla's own attachment point by the tip: across aspect ratios, world and hand FOV, the rod's equip dip, swing and sway, view bob, hurt tilt and nausea warp, the camera's smoothed eye height, and resource packs that redraw the rod. On a player's body (third person, other players, sleeping in any view) it is placed on the tip of the rod the body is drawn holding, in whatever pose the model is in.

Each Minecraft version lives on its own branch and the code differs per version family (see Versioning). This branch targets **MC 1.20–1.20.1** (obfuscated: yarn mappings, remapped by Loom; built and tested against 1.20.1, the jar declares `>=1.20 <=1.20.1` and is named `fishingrodfix-1.20-1.20.1-v<mod_version>.jar`). This is the oldest renderer the current fix runs on. Like `1.21.1` it has **no render states and nothing deferred**, and it goes one step further: there is **no `getHandPos` either**. `FishingBobberEntityRenderer.render(FishingBobberEntity, F, F, MatrixStack, VertexConsumerProvider, I)` computes the origin inline in a first-person and a third-person branch and then draws the catenary — a 17-iteration `renderFishingLine` loop into `RenderLayer.getLineStrip()` — in the same call. Held items go through `HeldItemFeatureRenderer.renderItem(LivingEntity, ItemStack, ModelTransformationMode, Arm, …)`, which hands `HeldItemRenderer.renderItem` the live stack and the entity itself (no `ItemRenderState`, no `ArmedEntityRenderState`); every pass of a frame draws into the `BufferBuilderStorage`'s one entity `VertexConsumerProvider.Immediate`; and `WorldRenderer` has no `renderEntities` method — the entity loop sits inside `WorldRenderer.render` and walks `ClientWorld.getEntities()`, an `Iterable`, not a list, so there is nothing to sort and vanilla never does. That order is `EntityIndex`'s `Int2ObjectLinkedOpenHashMap`, i.e. the order the client added the entities, which already draws a body before the hooks it cast; the branch forces it anyway, because Iris regroups that iteration by entity type whenever it is installed (see the Architecture section).

Compared with the `1.21.1` branch (this port's reference), the fix is the same logic against a still older renderer. What changed, and what it cost:

- **No `getHandPos`.** 1.21 extracted vanilla's origin into a method with one first-person `Vec3d.add(Vec3d)`; 1.20.1 builds it inline. The first-person branch ends with the method's **only** `Vec3d.rotateX(float)` (`vec3d = vec3d.rotateX(-k * 0.7F)`), so that is the `@ModifyExpressionValue` target, with `allow = 1`. Its value is an offset from the owner's **lerped feet**, not a world point: `render` adds the lerped feet to it and puts `getStandingEyeHeight()` into the line's y offset further down, so the hook adds both back to reach the world point `FishingLineOrigin` works in and takes them off again to return. The eye height is vanilla's own call on the same entity, made a few instructions later in the same branch.
- **The per-hook decision moved to the bobber's own position.** 1.21.1 decides right after `render`'s `getHandPos` call. Here the first call past the two origin branches is `fishingBobberEntity.getX()` — the one `getX` call in the method whose owner is `FishingBobberEntity` (the owner's is `PlayerEntity.getX`), so the selector needs no ordinal and neither branch's bytecode layout matters.
- **The line offset locals moved again.** 1.21.1's `k`/`l`/`m` are float ordinals 4–6; 1.20.1's `v`/`w`/`x` are float **ordinals 6–8** (LVT slots 38–40). The method's float locals in slot order are the two parameters `f`/`g`, the swing pair `h`/`k`, the body yaw `l`, the eye-height term `r`, and then the three offsets.
- **The camera's local axes are different.** 1.20.1's `Camera.setRotation` builds `rotationYXZ(-yaw, pitch, 0)`, whose local axes are +Z forward, +Y up and **+X left** (`moveBy(forward, up, left)`), so a view vector `(x right, y up, z back)` goes into the quaternion as `(-x, y, -z)`. 1.21.0 changed the quaternion to `rotationYXZ(π - yaw, -pitch, 0)`, where the same vector goes in unchanged. This is the one place in the math that differs between the two branches, and it is invisible in a build error.
- **No tick manager.** `/tick freeze` arrived in 1.20.3, so there is no `TickManager` and every entity is drawn at the frame's own tick progress: `ThirdPersonLineOrigin` uses it for the owner and the hook alike, with no `shouldSkipTick`. It also means MC-311645 (the line stuttering under a frozen tick rate) cannot happen here, so the README doesn't list it.
- **The frame's tick progress needs an accessor.** 1.20.1 has no `MinecraftClient.getRenderTickCounter()`, and its public `getTickDelta()` is the counter's field alone, which keeps running while the integrated server is paused. `MinecraftClient.render` passes `this.paused ? this.pausedTickDelta : this.renderTickCounter.tickDelta`; `FishingRodFix.tickDelta` mirrors that through `MinecraftClientAccessor` (the branch's only new mixin). `Camera` has no `getLastTickDelta()` here either, so `HandPass`'s camera-at-eye test uses the same value — the one `renderWorld` hands `Camera.update`.
- **The frame counter sits on `Mouse.getX()`.** 1.20.1's `GameRenderer.render(F, J, Z)` has no `MinecraftClient.isFinishedLoading()` call; the first call inside its `!skipGameRender` block is `this.client.mouse.getX()`, and it is the only one in the method. Past the skip is what matters (Dynamic FPS).
- **Method signatures.** `renderWorld(float, long, MatrixStack)`, `renderHand(MatrixStack, Camera, float)` (still with its own single `getFov` call and still called at the end of `renderWorld`, after the entities), `WorldRenderer.render(MatrixStack, F, J, Z, Camera, GameRenderer, LightmapTextureManager, Matrix4f)`, and `VertexConsumerProvider.Immediate.layerBuffers` is a `Map<RenderLayer, BufferBuilder>`.
- **Java 17.** `release 17`, `compatibilityLevel: JAVA_17`, `depends.java >=17`, and the loader floor is `>=0.12.0`. This is the only branch that **shades MixinExtras** into the jar: `io.github.llamalad7:mixinextras-common:0.5.5`, relocated to `com.andrewchik.fishingrodfix.shadow.mixinextras` by build.gradle's `shadeJar` and started by `MixinExtrasBootstrapPlugin`, the mixin config's `plugin`. The fix needs `@ModifyExpressionValue`, `injector.v2.WrapWithCondition` and `@Local`, and the other two ways of getting them both stop short of the loaders players are on: the **loader's own copy** means `>=0.15.7` (the first loader whose MixinExtras, 0.3.5, has `injector.v2`; 0.15.0–0.15.6 ship 0.3.0–0.3.3 and nothing before 0.15.0 ships one at all), and **nesting `mixinextras-fabric`** (Jar-in-Jar) means `>=0.14.25`, which that mod declares for itself in every release from 0.3.0 on and which the loader enforces on nested mods. **Fabulously Optimized pins 0.14.21 for 1.20 (pack 5.0.0-alpha.1) and 0.14.23 for 1.20.1 (pack 5.4.1, stable)** — below both, and the 1.20.1 pin is the reported failure, verbatim: `Reason: [HARD_DEP fishingrodfix 0.6 {depends fabricloader @ [>=0.14.25]}, HARD_DEP mixinextras 0.3.5 {depends fabricloader @ [>=0.14.25]}]`. Shaded, the jar asks the loader for nothing MixinExtras-shaped and the floor falls to what the rest of the metadata needs: `breaks`, i.e. `>=0.12.0`, where Fabric Loader first enforces `depends`/`breaks`. `JAVA_17` adds nothing above it (that level is in `CompatibilityLevel` back to sponge-mixin 0.10.2, which loader 0.12.0 pins) and neither does MixinExtras 0.5.5 itself, which handles Mixin 0.8 through 0.8.7. The low floor is behaviour-free: the Fabric Mixin bucket the loader applies is 0.10.0 for any floor from `>=0.12.0` to just under `>=0.16.0`, so `>=0.12.0` and the old `>=0.14.25` are the same bucket — and the classes Mixin exports for every target on loader 0.19.5 are byte-identical between the shaded build and the nested one. **Measured** (production client, jar in `mods/`, `-Dmixin.debug.countInjections`, 14/14 mixins and the title screen each time): loaders 0.14.11, 0.14.21, 0.14.23, 0.14.25 — no loader copy exists there, ours is the only MixinExtras — and 0.19.5, where the loader's own 0.5.5 is loaded as well: the log reads `Initializing MixinExtras via com.andrewchik.fishingrodfix.shadow.mixinextras.service.MixinExtrasServiceImpl(version=0.5.5)`, with no duplicate-class or bootstrap complaint and the same WARN set as the nested build — the two copies arbitrate over one shared Mixin blackboard key (`MixinExtrasServiceInstance`, a plain string the relocation does not touch), and whichever is in control serves both packages. Which one that is at equal versions is load order, not a rule: `shouldReplace` is a strictly-greater comparison, so on a tie the copy that bootstraps second concedes, and ours bootstraps at the first transformed class, the loader's at its `preLaunch` entrypoint. Either outcome is the same code. Don't read a future log that names `com.llamalad7…` there as a failure. **Below the floor the loader stops before the mod does:** 0.12.0 and 0.13.3 cannot start 1.20.1 at all, with or without mods — their tiny-remapper's ASM rejects LWJGL 3.3.1's `META-INF/versions/19/` entry (*Unsupported class file major version 63*) — and 0.14.0 dies in its own version parser. 0.14.11 is the oldest loader this was made to run on.
- **`Identifier.ofVanilla` doesn't exist**: `RodSprite` uses `new Identifier("item/fishing_rod_cast")`.

Everything else is 1.21.1's code under the same yarn names. `HeldItemRenderer` is the same class field for field and branch for branch (`mainHand`/`offHand`, `equipProgress*`/`prevEquipProgress*`, the package-private `getHandRenderType`, the idle branch's inline swing translate followed by `applyEquipOffset` and `applySwingOffset`, the `item.isOf(Items.FILLED_MAP)` map test, the `isUsingSpyglass` guard at the top of `renderFirstPersonItem`), so `FirstPersonRod` and the hand-pass half of `FishingLineOrigin` carry over unchanged. So do the nausea/portal warp (`renderWorld` spins it by `(ticks + tickDelta) × (the nausea effect held ? 7 : 20)` degrees from a private `int ticks`, intensity straight from `ClientPlayerEntity.nauseaIntensity`, no `max(…, getEffectFadeFactor(NAUSEA))`), `GameRenderer.getFov` returning a `double`, the public ABGR `NativeImage.getColor`, `SpriteContents` without `isAnimated()` (its private `getFrameCount()` stands in), the missing `getArmHoldingRod` and `getStackInArm`, `LivingEntityRenderer`'s inline body-yaw clamp (85° head limit, the 50°/0.2 rider turn), `Transformation.apply`'s left-hand fix, and `ItemRenderer.renderItem`'s display transform followed by `translate(-0.5, -0.5, -0.5)`. `handheld_rod.json` and `fishing_rod_cast.png` are byte-identical to 1.21.1's, so the measured vanilla rod tip is the same `(15, 1)/16`, and `rendertype_entity_translucent_cull.fsh` still discards `color.a < 0.1`. The `applyEquipOffset`/`applySwingOffset` constants (0.56, −0.52, −0.72, −0.6; 45/−20/−20/−80/−45), the sway factor 0.1°/degree and the line's 0.25 lift hold, and the hand pass has no swing animations and no swap-animation scale.

**1.20–1.20.1 is one jar** (see Versioning for the coverage decision). ~99% of that line's players are on 1.20.1, and the older published `fishingrodfix-1.20-1.20.4-v0.5.jar` still covers 1.20.2–1.20.4. The upper bound is closed (`<=1.20.1`) rather than `<1.20.2`: Fabric normalises a snapshot or pre-release into a semver pre-release of the *next* release (`1.20.2-alpha.…`), which sorts below `1.20.2` and would satisfy `<1.20.2`.

## Build Commands

```bash
# Build the mod (produces JARs in build/libs/)
./gradlew build

# Run the Minecraft client with the mod loaded
./gradlew runClient

# Generate sources and set up IDE
./gradlew genSources
```

CI builds with Java 21 but compiles to `release 17` (Minecraft 1.20.1's own Java level); `gradle/gradle-daemon-jvm.properties` makes Gradle run on a JDK 21 for this branch (Loom 1.17 needs it, and Loom 1.18+ would need Gradle on JDK 25). `genSources` asks its decompiler worker for 4 GB; on a machine short of commit memory, lower it for one run with an init script (`loom.decompilerOptions.each { it.memory.set(1536L) }`) rather than changing the build file.

## Architecture (1.20–1.20.1)

Purely client-side; no access widener and no Fabric API dependency. MixinExtras is shaded into the jar under `com.andrewchik.fishingrodfix.shadow.mixinextras` rather than taken from the loader or nested as a library mod, which is what lets this branch run on the loaders Fabulously Optimized ships (see the Java 17 note above). Loom remaps the mixins' targets to intermediary itself (no refmap), and that is exactly why `shadeJar` runs **after** `remapJar` and never before: tiny-remapper recognises MixinExtras' annotations by their real names (`net.fabricmc.tinyremapper.extension.mixin.common.data.Annotation` hardcodes `Lcom/llamalad7/mixinextras/injector/ModifyExpressionValue;`, `…/injector/v2/WrapWithCondition;` and the rest), and with no refmap those annotations' `method` and `at.target` strings are the only place the intermediary names live — relocate first and all five `@ModifyExpressionValue` and the `@WrapWithCondition` keep yarn names in a jar that runs against intermediary, six injectors that silently never apply. v0.5 on this branch was one mixin plus an entrypoint and an access widener for `GameRenderer.getFov`, all removed.

- **`FishingBobberEntityRendererMixin`** (`src/client/java/.../mixin/client/`) — everything the hook's own `render` needs, in the order that method runs (its full descriptor is spelled out at every injection, because a synthetic bridge `render(Entity, …)` exists). A HEAD `@Inject` resets the per-hook flags. A `@ModifyExpressionValue` (`allow = 1`) on the method's only `Vec3d.rotateX(float)` — the last step of vanilla's first-person branch — delegates to `FishingLineOrigin`, or keeps vanilla's value while vanilla draws the player's own body (asleep, or a third-person camera on the player in first person), whose rod `ThirdPersonLineOrigin` takes; the value there is an offset from the owner's lerped feet, with `getStandingEyeHeight()` added into the line's y further down, so the hook converts both ways around `FishingLineOrigin`'s world point. Where `FishingLineOrigin` keeps vanilla's value with the camera on the player, it tells `ThirdPersonLineOrigin` (a flag reset at HEAD), whose line then only moves onto a body drawn earlier in the same pass. The third-person branch isn't hooked: players other mods send down it (First Person Model; Real Camera) get the body-held rod too. An `@Inject` at the method's only `FishingBobberEntity.getX()` call — the first instruction past both branches — decides the line's visibility and whether it moves onto the owner's drawn rod (vanilla's own `playerEntity` local via `@Local`; it is never null there, because vanilla returns before that point without an owner, and the helpers still take a null owner as cheap defence against a mod that nulls the local). Three `@ModifyVariable`s at the STORE of float ordinals 6/7/8 (`v`/`w`/`x`, LVT slots 38–40) write the body-held offset, the first of them also being where that offset is worked out, since the pose there is the one the catenary is drawn with. A `@WrapWithCondition` on the one `renderFishingLine` call site, which the loop reaches once per segment, skips a hidden line. The three `@ModifyVariable`s and the `@WrapWithCondition` are `require = 0`, as on the render-state branches: losing the offsets or the condition leaves the line at vanilla's value, where a required injector would mean a startup crash for everyone running a mod that owns the same site. The two `@Inject`s and the `@ModifyExpressionValue` are required — the MEV carries `allow = 1` and no `require`, so it inherits the config's `defaultRequire: 1`: a second `Vec3d.rotateX` or a missing `FishingBobberEntity.getX` would mean this branch's reading of vanilla had broken, and failing to load beats a silently misplaced line.
- **`FishingLineOrigin`** — replaces vanilla's guess (it doesn't reuse vanilla's eye-based vector): reads what this frame's hand pass will draw with (`HeldItemRenderer.renderItem` runs from `GameRenderer.renderHand` at the end of `renderWorld`, after the world's entities are drawn, and reads the live player and the renderer's own drawn items and equip progress, `HeldItemRendererAccessor`, at the frame's tick progress; nothing ticks in between, so the same reads while the entities are drawn match; its package-private `getHandRenderType` is mirrored), takes the rod's line attachment point from `FirstPersonRod`, applies vanilla's item sway and own view bob/hurt tilt (`GameRendererInvoker`), and places the world point, relative to the camera and with the world-only nausea/portal warp undone (its spin through `GameRendererAccessor`), on the pixel where the hand pass draws that point. The view-to-world step negates x and z before rotating by the camera quaternion, because 1.20.1's camera is built as `rotationYXZ(-yaw, pitch, 0)` with +X left (see the Project Overview). Both FOVs are the ones vanilla's own `GameRenderer.getFov` returns for this frame, so zoom mods that hook it are followed: `GameRendererMixin` captures each (optional `@ModifyExpressionValue`s on the `double` it returns here), the world FOV at `renderWorld`'s only `getFov` call, before the entities are drawn (this frame's), and the hand FOV at `renderHand`'s only one, which runs at the end of `renderWorld` after them (so last frame's, used while the world FOV's factor on top of its options-FOV-times-movement-modifier base is unchanged within rounding: that factor holds the death and fluid factors, which the hand FOV shares, and any zoom a mod multiplies in; so sprinting, speed and flying don't count; otherwise, or without the captures, `getFov` is asked through `GameRendererInvoker`: each call probes the camera's surroundings for fluid, `Camera.getSubmersionType`, a dozen world lookups and ~1 KB of garbage); 1.20.1 keeps no copy of the world projection without the bob and warp, so a mod that changes the projection itself isn't followed. The rod's hand comes from the drawn items; while a rod is held but none is drawn yet (a quick F-swap with a hook out) the line stays with the hand it was last drawn in. None of its inputs change within a frame (the player and the renderer's fields only in ticks, the camera once per frame), so the origin is worked out once per `HandPass` frame and reused by every later hook of the local player in it (Iris' shadow pass draws them first, before the world's own entity loop and its hand pass; nothing it reads changes in between); a panorama capture, which renders the world without a frame of its own, is checked before that reuse. Its class Javadoc lists the steps and every case that keeps vanilla's value.
- **`FirstPersonRod`** — vanilla's first-person rod geometry. The attachment point is vanilla's screen anchor `(±0.525, -0.1)` back-projected, at the 70° hand and an assumed 16:9 calibration aspect, onto the resting rod's model mid-plane, shifted by the pack's tip delta (`RodSprite`), then carried through `renderFirstPersonItem`'s idle branch (its swing translation, then `applyEquipOffset` incl. the equip dip, then `applySwingOffset`; the two translations commute) and the `handheld_rod` display transform. 1.20.1 has no swing animations (every idle item swings the same way) and no swap-animation scale.
- **`ThirdPersonLineOrigin`** + `HeldItemFeatureRendererMixin` / `AbstractClientPlayerEntityMixin` — the line origin on a rod held by a player's body, for every line not on the first-person rod: vanilla's third-person branch for every player (MC-4490 crouch, MC-176514 riding, MC-198777 boat, MC-247425 arm swing, MC-270173 swim/crawl, MC-270174 sleep; also walking, gliding, riptide, death), and the local player whose body is drawn in first person (asleep, a mod's third-person camera, a mod drawing it such as Player Animation Library's first-person model mode). Vanilla's third-person value is a fixed offset from the eye turned by the entity's body yaw. Nothing of the pose is modelled: the rod is read where it is drawn. `HeldItemFeatureRendererMixin` (`require = 0`, priority 1500 so it runs after other mods' same-call `@Inject`s, e.g. animation and held-item position mods) sits at `HeldItemFeatureRenderer.renderItem`'s `HeldItemRenderer.renderItem` call, past its empty check, so once per non-empty held item of an armed entity: a small inlined gate (the drawn stack is a fishing rod and the entity is an `AbstractClientPlayerEntity`) leads to the out-of-line read, which for a fishing player (`PlayerEntity.fishHook` is set on the client) whose rod is in the arm the line starts at (`FishingRodFix.armHoldingRod`, mirroring `render`'s own side factor) stores on the player (`AbstractClientPlayerEntityMixin`) the attachment point under the drawn pose, tagged with the pass (frame + the number of passes that have ended so far + either the buffer source or, for a drawing inside the world's entity loop, that loop). `PlayerHeldItemFeatureRenderer` overrides that method but delegates to it for everything except a raised spyglass, so a player's rod comes through. The body's lerped position and yaw are recomputed the way the entity loop and `LivingEntityRenderer` do, at the frame's tick progress (1.20.1 has no tick manager, so every entity gets it). **The pass tag**: on 1.20.1 nothing is deferred and one `VertexConsumerProvider.Immediate`, the entity one, takes every vanilla pass of a frame — the world's entities and block entities, the first-person hand, the screen effects, and the GUI's pictures such as the inventory's player model. Two optional hooks end a pass: `WorldRendererMixin` marks the first `WorldRenderer.checkEmpty(MatrixStack)` call, the second statement after the entity loop (priority 1500, so a body other mods draw at that same call — Freecam's Show Player — is still part of the entity pass), and `VertexConsumerProviderImmediateMixin` counts `VertexConsumerProvider.Immediate.draw()`. The first keeps the GUI's pictures apart from the world's entities even when a mod replaces the buffer sources so vanilla's `draw()` never runs (ImmediatelyFast's `BatchableBufferSource` overrides it without calling super); the second separates passes that share one entity loop. `OutlineVertexConsumerProvider` is not an `Immediate` here, but its `draw()` flushes an `Immediate` of its own, so it marks a pass too — it runs after the block entities, well past the entity loop. Nothing inside the entity loop flushes, so a rod and a hook of the same loop stay in one pass; with neither hook applied no pass is ever matched, and every body-held line keeps vanilla's value. The collector alone would not do, because a mod may hand each entity its own — **Iris with a shader pack** does: its `entity_render_context/MixinEntityRenderDispatcher` `@ModifyVariable`s the buffer-source argument of every `EntityRenderDispatcher.render` into a freshly allocated `BufferSourceWrapper` as soon as a pack has set `WorldRenderingSettings.entityIds`, which nothing resets, so it outlives unloading the pack until the game restarts, and a rod and its hook never share one. What they do share is the loop: `WorldRendererMixin`'s hook at the start of the entity loop records the pass that loop opens in (frame + pass-end count) before the first entity, every drawing notes whether it happened while that record still held, and the match takes two such drawings of one loop as the same pass however their collectors differ. The pose is the loop's own `MatrixStack` either way, which is what the collector was ever a proxy for. Iris' shadow pass never goes through that loop and is drawn before the record is taken, so its drawings see the previous frame's record and note themselves as outside (it keeps pairing by collector, as before — and since a shadow pass only exists with a pack, that means per-entity wrappers and no pairing at all); the GUI's pictures are past the loop's end mark and past every buffer-source flush, so their pass-end count differs; and without the optional hook nothing is ever inside a loop and the match is the collector's alone, exactly as before. A body drawn inside the loop but into another collector is now matched where it used to miss — a glowing player or a spectator's outlines (`OutlineVertexConsumerProvider`), and a mod's own buffer source used inside the loop. **Which of the two comes first is forced** by `ThirdPersonLineOrigin.bobbersLast`, an optional `@ModifyExpressionValue` on the one `Iterable.iterator()` call in `WorldRenderer.render`: the wrapper it returns yields every non-bobber in the source's order and the bobbers after them, so the bodies are drawn first and every body-held line sits on the rod of this very frame. Vanilla 1.20.1 would not need it — `ClientWorld.getEntities()` is the client's add order (`EntityIndex` keeps the entities in an `Int2ObjectLinkedOpenHashMap`), nothing sorts or copies it, and a player is added before the hooks it casts. **Iris does.** Its `MixinLevelRenderer_EntityListSorting` (mixin priority 999, in `iris-batched-entity-rendering.mixins.json`, which is *not* gated on a shader pack being in use) `@WrapOperation`s this very `Iterable.iterator()` call and regroups every entity by `EntityType` through a `HashMap` so its entity batching sees one type at a time; `EntityType` inherits `Object.hashCode`, so which of the player and fishing-bobber groups lands first is an identity hash — arbitrary, fixed for the session, different in every launch. At mixin priority 1500 this modifier applies after Iris' wrapper, which makes it the outer one: it sees Iris' regrouped iterator and settles the order. The wrapper is lazy — it pulls from the source only as the loop asks, hands every non-bobber straight on, and starts allocating a list only when it meets a bobber; by the time the source is exhausted every bobber is in it. With no bobber in the world it is a type check and two reference field writes per *iterated* entity — every entity `ClientWorld.getEntities()` yields, i.e. every loaded one, before the frustum cull drops most of them — plus one wrapper object per frame, against the frustum test, block-position lookup and full entity render vanilla does for each of them in the same loop. It cannot throw on its own (it only delegates, tests a type and appends), so there is nothing to guard. Reordering is as close to free of consequence as the renderer allows: `entity_cutout` on the bobber's texture is opaque and depth-writing and `line_strip` blends but writes depth and carries alpha 255, neither is a `translucent` layer (so neither is quad-sorted at draw time), no translucent layer moves relative to another, a glowing bobber's outline copy carries the colour set for that entity right before it draws (`entity_cutout` does affect the outline, `line_strip` doesn't), and neither bobber layer has a dedicated allocator in `BufferBuilderStorage`, so a bobber costs its two draw calls wherever it sits and moving one contiguous run is worth at most one draw call at the seams, only ever one fewer — and with Iris' batching in front of it, a contiguous run moved to the end keeps every other type's grouping intact. What is left is the one pairing a reorder can decide: a bobber behind an entity layer that blends and writes depth, which `entity_translucent` does and every player body uses (`PlayerEntityModel`), so it is now always drawn after that body and depth-rejected; the layer's 0.1 alpha cutout and skins being alpha 0 or 255 make that a non-event. The per-hook decision, its owner's partial tick and the same-pass-only flag are three fields set at the bobber's own `getX()` call and consumed where the first offset local is stored, in the same call — no object reference, nothing to outlive the drawing; the pending offset is cleared once `x` is written and the last hook's pass (its buffer source) at the next frame's start (`GameRendererMixin`). Where the first offset local is stored, when the owner's rod was drawn earlier in the same pass, the line offset is that point through the inverse of the hook's pose (a pass that turns its root cancels out), minus the line's 0.25 lift. Otherwise it is the tip where the rod was last drawn, relative to the body's position and turned with its yaw, while the owner still holds a rod in that arm; a pose or mount change invalidates that offset, and it is kept anyway, because a one-frame lag is far less visible than a one-frame teleport — not because it is the closer of the two candidates. Usually it isn't: measured against the tip as drawn on the transition frame, vanilla's value is nearer for most of them (leaving gliding or a riptide spin 2.15 blocks or more for the kept reading against 0.12, waking 0.8–2.1 against 0.12, a crouch 0.54 against 0.07), and the kept reading only wins leaving swimming (1.04 against 2.12) and lying down (0.81 against 1.39); a mount change or a lean that ramps up is small either way. What the leniency buys is the frame the origin would otherwise jump to a different anchor and back, which is the visible artifact; in vanilla's own order this whole path is a fallback rather than the usual one. The yaw re-rotation follows the pose the reading was taken in, which is the convention the offset is in. The remembered offset carries the render offset of the frame it was read in (`EntityRenderer.getPositionOffset(T, float)`, which the pose includes and the body position it is measured against does not): it cancels while that offset holds, and a player's is only the crouch shift, which the remembered path's pose gate keeps in step (the experimental minecart's lerp, the other part from 1.21.2 on, does not exist here), so on this branch it cancels outright. Re-deriving it would mean re-deriving a vanilla method any mod may override, at the reading and at the replay. An older reading isn't kept; else vanilla's value. A first-person line `FishingLineOrigin` left at vanilla's value (see its Javadoc) with the camera on the player takes only the same-pass rod, never the remembered one: no body is on screen, and the remembered spot (from an F5 view just left, or from Iris' shadow pass, whose entity collection doesn't skip the camera entity as `WorldRenderer`'s does and so draws the local body with its rod and its hook) would start the visible line at a rod that isn't drawn. Iris' shadow pass carries no line of its own either: it exists only with a shader pack, and with one every entity render gets its own buffer source, so its rod and its hook never pair (it never goes through `WorldRenderer.render`'s loop either, so the loop tie doesn't reach it, and it sorts its own list by the same identity hash). Player Animation Library's first-person body (drawn earlier in the world pass) still carries the line. With the camera on another entity vanilla never draws the local player, so a drawn body is a mod's and may come after the hooks: that line keeps the remembered spot. The remembered offset is taken whenever a hook of the pass gives the world position, before or after the rod (a mod may draw the body after the hooks). Exceptions disable it until the next world; without frame counting nothing is read.
- **`ThirdPersonRod`** — the body-held rod's attachment point in the space `HeldItemFeatureRenderer` draws the item in: the rod's tip (`RodSprite`; not first person's vanilla anchor, which sits by the tip only at first-person scale and angle) on the model mid-plane, through the `handheld_rod` `thirdperson_righthand` display transform that `ItemRenderer.renderItem` applies two calls further in (the left hand's is the same after `Transformation.apply`'s left-hand fix). Cached per frame.
- **`RodSprite`** — the tip of the `item/fishing_rod_cast` sprite, the rod model's source in every view (on 1.20.1 in the block atlas, which holds the item textures: `JsonUnbakedModel` resolves an item model's textures against `SpriteAtlasTexture.BLOCK_ATLAS_TEXTURE`, which is deprecated but is still the key `BakedModelManager.getAtlas` takes): a resource pack's redrawn sprite is measured (visible pixels at/above the alpha cutout of 0.1, which `rendertype_entity_translucent_cull.fsh` — the layer `RenderLayers.getItemLayer` picks for a direct-rendered non-block item — discards below, unioned over animation frames; a shift beyond `MAX_TIP_SHIFT`, the one tuned constant in the rod geometry, is ignored as a misread), cached per `SpriteContents` identity, i.e. per resource reload. 1.20.1 has no `SpriteContents.isAnimated()`, so its private `getFrameCount()` stands in (`SpriteContentsAccessor`): it is `> 1` exactly when the sprite has an animation, and only then are the `getDistinctFrameCount()` tiles read instead of tile 0. The tile grid is not a substitute — an `.mcmeta` sizes the sprite even when its frame list collapses to a null animation, so a multi-tile image can be unanimated. Pixels come from the public `NativeImage.getColor`, which returns ABGR here (1.21.5 replaced it with the ARGB `getColorArgb`); the alpha is the top byte either way.
- **`FishingLineVisibility`** + `FishingBobberEntityMixin` — hides the line (not the bobber) of a hook whose rod has left its owner's hands, in every perspective and for every player (MC-310980, MC-211561): the server removes such a hook only a tick plus the ping later. Where `FishingLineOrigin` placed the line on the drawn first-person rod, it stays until the lowering rod is gone from the drawn items (a first-person line left at vanilla's value hides at once: vanilla would start it at the off-hand side, where no rod is). Only hooks whose owner was seen holding a rod (a flag on the hook) are hidden, so hooks cast by other items — including a modded rod that isn't `minecraft:fishing_rod` — keep vanilla's line; for the local player a rod among the drawn items counts too (the own hook arrives a round trip after the cast). Decided at `render`'s `FishingBobberEntity.getX()` call and applied by a `@WrapWithCondition` (MixinExtras v2) on the one `renderFishingLine` call site in the same call, which its loop reaches once per segment; 1.20.1 has no render state to carry the decision on and needs none, since both sit in one method. An exception leaves lines visible until the next world or dimension. Hiding a line coexists with **Iris**, whose always-loaded `MixinFishingHookRenderer` appends one degenerate vertex to `line_strip` at this same method's second `pop()` (`require = 1`): the wrap removes no instruction, so Iris' point and both `pop()`s survive, and with the 17 segments skipped that lone vertex is duplicated by the buffer builder into a two-vertex strip whose zero normal the lines shader turns into a NaN position — nothing drawn, nothing thrown. The three `@ModifyVariable`s keep their ordinals under Iris' inject too: Mixin resolves every injection point in its `PREINJECT` pass before applying any, and Iris' point is after the three float stores in any case.
- **`HandPass`** + `GameRendererMixin` / `HeldItemRendererMixin` — whether the hand pass reached a hand last frame (frames counted at `GameRenderer.render`'s only `Mouse.getX()` call, i.e. once per rendered frame, the first call inside its `!skipGameRender` block, through which Dynamic FPS skips most frames while throttling (a skipped frame counted as one without a hand would put the line at vanilla's value), the frame marked where the five-argument `HeldItemRenderer.renderItem` calls `renderFirstPersonItem`, past any cancel; also reached while scoping, where nothing is drawn, so `FishingLineOrigin` checks scoping itself). No rod on screen → vanilla's value, whatever hid the hand (spectator, a mod cancelling the hand pass), unless the player's own body is drawn with the rod in the world pass (asleep, a third-person camera; Player Animation Library's first-person model mode, whose body counts only when drawn earlier in the same pass than the hook): then `ThirdPersonLineOrigin` puts the line on that rod. The HUD hidden with F1 is the exception: it hides the hand but not the line, a world object, so the line stays corrected where the rod would be. The frame counter runs before the camera update, which 1.20.1 does inside `renderWorld` (no separate `updateCamera`), so right after `renderWorld`'s `Camera.update` call (after the tick, before the entities and the hand pass) `HandPass` samples the live `GameOptions.hudHidden` (which `renderHand` reads later in the frame) and the rest of `renderHand`'s gate (first person, not rendering a panorama, awake, not spectating), plus the camera on the player, not in third person and at the player's eye where `Camera.update` puts it (some freecam mods keep the player as camera entity and don't move the camera into third person; the smoothed eye height comes through `CameraAccessor`). At the next frame's start it latches whether a hand is drawn when only the HUD decides, from frames that prove it (a drawn hand; a missing one with the HUD and the gate open means a mod hid it); a frame with the gate closed, or one that didn't render the world, restores the default (drawn). While the HUD is hidden (this or the previous frame) the line stays corrected if that latch holds and the gate is open this frame. So a hidden HUD never moves the line (Camerapture's photo frame and freecams on their own camera entity keep vanilla's value, unless they draw the player's body: then the body's rod, one frame late, from the remembered spot; freecams that move the player's camera into third person keep the body's rod; F5, sleep or spectator before F1 don't stick). Mods that keep the hand while hiding the HUD (Better F1) stay corrected through the normal path. These injects are `require = 0`: if the counter or the mark is blocked, the line just stays vanilla, and `FishingLineOrigin` logs one warning (frame counter never ran, or no hand mark seen while fishing in first person); without the sampling, F1 leaves vanilla's line.
- **`MinecraftClientAccessor`** — `@Accessor`s for `MinecraftClient.renderTickCounter` and `pausedTickDelta`, the two halves of the frame's tick progress (`FishingRodFix.tickDelta`). **`SpriteContentsAccessor`** — `@Accessor` for `SpriteContents.image` and `@Invoker` for its private `getFrameCount()`, which stands in for the `isAnimated()` 1.20.1 doesn't have. **`CameraAccessor`** — `@Accessor`s for `Camera.cameraY`/`lastCameraY`. **`GameRendererInvoker`** — `@Invoker`s for `GameRenderer.tiltViewWhenHurt`/`bobView`/`getFov` (the last returns a `double` here). **`GameRendererAccessor`** — `@Accessor`s for `GameRenderer.ticks` (the warp's spin counter; 1.21.5 replaced it with a `nauseaEffectTime`/`nauseaEffectSpeed` pair) and `fovMultiplier`/`lastFovMultiplier` (the movement FOV modifier, for the shared FOV factor). **`HeldItemRendererAccessor`** — `@Accessor`s for `HeldItemRenderer`'s drawn items and equip progress. **`VertexConsumerProviderImmediateMixin`** — counts `VertexConsumerProvider.Immediate.draw()` calls for `ThirdPersonLineOrigin`'s pass tag (`@ModifyExpressionValue`, `require = 0`, on the method's only field read, so nothing is allocated). **`WorldRendererMixin`** — two optional hooks on `WorldRenderer.render` (`require = 0`, mixin priority 1500 so both apply after other mods' default-order and lower-priority injectors at the same call): a `@ModifyExpressionValue` on its one `Iterable.iterator()` that puts the fishing bobbers behind every other entity (Iris regroups that iteration by entity type, so without this the order would be an identity hash), and an `@Inject` at the first `checkEmpty(MatrixStack)` call, five bytes past the `drawCurrentLayer()` that closes the entity loop, which marks the pass end for the same tag and is what still separates the world's entities from the GUI's pictures when a mod replaces the buffer sources. The mark sits at `checkEmpty` rather than at the flush because mods that draw one more body at the end of the entity loop hang it on that very call (Freecam's Show Player), and at priority 1500 this callback runs after theirs, so such a body is still inside the pass. **`FishingRodFix`** — the shared logger, `isRod`, `armHoldingRod`, `stackInArm`, `holdsRod` and `tickDelta`.

Declared incompatible: Enchanted Fishing Line (`enchanted_fishing_line`, all versions) is listed under `breaks` in `fabric.mod.json`, so the loader refuses to start with both and shows its incompatible-mods screen. On the newer branches its builds were found to carry a copy of this mod's v0.5 correction, applied on top of v0.6's with no check for this mod. It ships a Fabric build for 1.20.1 too (`1.0.0`, checked 2026-09-23 on Modrinth: 1.20.1, 1.21.1, 1.21.11, 26.1.x and 26.2), so the entry is live here — but the mod is closed source (no repository, empty `source_url`) and what its 1.20.1 build hooks is unverified; on this version there is no `getHandPos`, no render state and no deferred `submit`, so the newer branches' description of the conflict does not transfer. User decision 2026-09-22: `breaks` on every branch, no EFL-specific code, whatever it turns out to hook.

Known limitations: per-item model swaps (server `custom_model_data`, CIT), 3D rod models and changed display transforms are not measured; mods that re-pose the hand in the renderer without touching the state it reads (viewmodel mods), shaderpack hand sway, portal-view mods that move the camera (Immersive Portals), Polytone's line offsets and Tide's own hook renderer are not covered; the hand pass reads the live player and its renderer's fields, and its hand selection (`HeldItemRenderer.getHandRenderType`) is mirrored, not read, so a mod that changes `renderItem`'s locals or arguments (swing, sway, equip dip, the drawn item) or that selection isn't followed (a hand it hides keeps the line at the hidden rod; one it draws where vanilla wouldn't keeps vanilla's value), while mods that change the renderer's fields (equip changes in `updateHeldItems`) are; the world FOV is `getFov`'s, so mods that change the world projection itself rather than `getFov` (an orthographic camera, a lens) aren't followed, nor, reliably, a zoom mod that restores the hand FOV with its own `@ModifyExpressionValue` on the very `renderHand` `getFov` call this mod captures (both chain, but the order between them is undefined, so the line can be off the rod while zoomed, as vanilla's is); mods that bob or sway the hand and world passes differently (BetterHandBobbing, View Bobbing Options, No Screen Bobbing, Tweakeroo's world view-bob toggle, ShakeTweaks' bob toggles and "Disable Hand View Sway"), leave the same mismatch vanilla has; mods that drop the nausea warp from `renderWorld` without Clearviews' mod id (anti-nausea in Meteor, Wurst, LiquidBounce) make the line swing around the rod under nausea/portal — the `clearviews` check `FishingLineOrigin` carries is inert on this branch, because the 2.x line that uses that id starts at 1.21 and the only 1.20.1 build is Clearview 1.x (mod id `clearview`), whose client mixins are the fog and the portal/spyglass overlays only — nothing on 1.20.1 removes the warp from `renderWorld`, so both passes get it; mods that hide one arm by cancelling its `renderFirstPersonItem` (Hide Hands, Exposure, Tweakeroo's Disable Offhand Rendering), or only its item (Player Animation Library during a first-person transition), leave the line at the hidden rod's tip, as do mods that hide the hand only after F1 was pressed (Camerapture's camera, Snapmatica's viewfinder, Picture Mode); conversely a mod that stops hiding the hand while F1 is on (Snapmatica's viewfinder or a freecam parked at the eye) leaves vanilla's line until F1 is released; camera-smoothing mods that move the camera off the eye without detaching it (SmoothCamera) drop the F1 line to vanilla's value while they do; a local cast followed by a slot switch before the hook reaches the client, on a ping longer than the drawn items' few-tick lag, keeps vanilla's line until the server removes the hook. On a player's body (third person): the rod is read where `HeldItemFeatureRenderer` draws it, so everything that poses the body, arm or item before that call is followed (animation mods, held-item position mods, First Person Model's offset body, Mine Little Pony's ponies), but not what changes the item after it (a resource pack's changed `thirdperson` display transform, per-item or 3D rod models, a wrap, redirect or argument change of that call, or a same-call `@Inject` above priority 1500), nor rods drawn outside the pass the hook's line is drawn in (a player with the glowing effect or a spectator's outlines, whose body goes into the outline buffer source while its hook stays in the entity one; Real Camera's binding mode, its default once enabled, which replays its own recorder; its classic mode draws the body at `WorldRenderer.render`'s first `Immediate.drawCurrentLayer()`, i.e. after the entity loop and five bytes before the pass end, so on 1.20.1 that line takes the remembered spot, one frame late, like Freecam's Show Player) or not through that feature renderer (morph mods such as Woodwalkers: vanilla's value). Where the owner's rod isn't drawn in the pass before its hook (the owner out of view, a hook that arrived before its owner, a body drawn after the hooks, such as Freecam's Show Player), the line starts where it was last drawn, turned with the body; a changed arm pose (a swing) shows when the rod is drawn again, a pose or mount change is followed only as far as a reading from the previous frame allows (one frame of pose change, then the next drawing settles it), and a player never seen with the rod drawn, or in another pose for more than a frame, keeps vanilla's value until it is drawn again (a jump then); a player who starts drawing another way in the same pose while fishing (a morph mid-cast) keeps that remembered spot. A rod hidden by another mod (Not Enough Animations' off-hand hiding) leaves the line where the rod was last drawn; hidden in bed (its default) the line keeps vanilla's value unless the rod was seen drawn in bed before. The value vanilla's third-person branch computes is untouched for a body-held rod (only `render`'s own offset locals are written), so a mod that reads it sees vanilla's. **With an Iris shader pack every body-held line keeps vanilla's value.** Iris' `entity_render_context/MixinEntityRenderDispatcher` replaces the buffer-source argument of every entity render with a freshly allocated `BufferSourceWrapper` as soon as a pack has set `WorldRenderingSettings.entityIds` (nothing resets it, so it outlives unloading the pack, until the game restarts), so a rod and its hook never share a collector identity, no pass ever matches, nothing is remembered and MC-4490, MC-176514, MC-198777, MC-247425, MC-270173 and MC-270174 are unfixed in that configuration; the first-person line is unaffected, and so is Iris without a pack. The same mixin is on Iris' 1.21.4 and 1.21.5 branches, so this is not specific to 1.20.1. A body drawn before the pass is recorded — i.e. before the entity loop's `iterator()` call — is outside the window. Nothing checked draws one there on this version: First Person Model hangs its body on `WorldRenderer.render`'s first `checkEmpty` call (yarn; `checkPoseStack` in Mojang names) at the default injector priority — the same call the port marks the pass end at, but at priority 1500, so the port's mark runs after First Person Model's draw — and its body is therefore inside the window and is matched even with an Iris shader pack (checked against First Person Model's `<1.21.3` arm, 2026-09-23). A mod rendering the world twice per frame into one buffer source without flushing it in between could hand one pass's rod to the other (vanilla's passes each end with a `draw()`, which ends a pass here). A hook drawn before its owner has no reading of this frame's rod: its line is one frame late for as long as that order holds (visible on a fast arm swing; a pose or mount change keeps the previous frame's reading rather than falling back to vanilla, so the origin never jumps to a different anchor for a frame — the lag is largest leaving swimming, gliding or a riptide spin and when lying down or waking), and a line `FishingLineOrigin` left at vanilla's value with the camera on the player (Player Animation Library's first-person body) keeps vanilla's value, since that case takes only a rod drawn earlier in the same pass. The bobbers-last wrapper (see the Architecture section) is what keeps that from being the normal case: vanilla's own order already puts a body first, but **Iris regroups the drawn entities by entity type through a `HashMap` whenever it is installed**, shader pack or not, which would otherwise make the order an identity hash — arbitrary per launch and fixed for the session. A mod that keeps that mixin from applying, draws the entities without going through `WorldRenderer.render`'s loop, or wraps the same call at a still higher mixin priority brings that coin toss back; on the losing side every body-held line is one frame late. What no draw order can fix is a hook the server sent before its owner, a body another mod draws after the hooks, and a hook whose pass the wrapper never sees (Iris' shadow pass, whose own list is sorted by the same identity hash) — all of them fall back the same way. The wrapper only orders the entities `WorldRenderer` itself draws.

## Dev environment gotcha

Loom writes `.idea/runConfigurations/Minecraft_Client.xml` only when it is missing and never updates it, and `.idea` is shared by every branch of the checkout. A stale config on the 26.3 branch lacks `-XX:StackShadowPages=32` (from Mojang's version JSON), and the client then dies natively on an in-world resource reload (access violation in `jvm.dll`, no `hs_err`). A 26.x config on an old branch fails to start on JDK 21 (`--sun-misc-unsafe-memory-access`). After switching version families, delete the XML and run `./gradlew ideaSyncTask`.

## Versioning

Each Minecraft version lives on its own branch (e.g. `1.20`, `1.21.1`, `1.21.4`, `26.3`). The version numbers in `gradle.properties` (`minecraft_version`, `loader_version`, `loom_version` — on branches not yet ported to the current fix the Loom version sits in `build.gradle`'s `plugins` block instead — and `yarn_mappings` on pre-26 branches) must be updated together when porting to a new MC version. The `mod_version` in `gradle.properties` is independent of MC version.

This branch's jar covers **1.20 and 1.20.1** from one build against 1.20.1. 1.20 and 1.20.1 are the same client as far as the fix is concerned. 1.20 → 1.20.1 changes 27 of the 7436 intermediary classes — GUI widgets, Realms, `ConnectScreen`, `ReporterEnvironment`, `SharedConstants`, `MinecraftVersion`, `ClientConnection`, `ChunkStatus` — none of them a class the mod mixes into, reads or inherits from, with the same 88 libraries, the same Java 17 and the same launcher arguments, and `handheld_rod.json`, `fishing_rod_cast.png` and `rendertype_entity_translucent_cull.fsh` byte-identical (checked 2026-09-23 with the intermediary-jar diff of the `/port-version` skill's Step 8). 1.20.2–1.20.4 are not in it. The injection *points* do survive to 1.20.4 — the same `render` descriptor and float LVT, one `Vec3d.rotateX`, one `FishingBobberEntity.getX`, the same `renderWorld`/`renderHand`/`WorldRenderer.render` signatures and INVOKE counts, `layerBuffers` still a `Map`, the same camera rotation — but two differences are behavioural: **1.20.3 added `TickManager`**, and 1.20.4's `WorldRenderer.render` picks each entity's tick delta with `tickManager.shouldSkipTick(entity)` before `renderEntity`, so this branch's "every entity at the frame's own progress" would be wrong there under `/tick freeze`; and 1.20.4's `Camera` has `lastTickDelta`/`getLastTickDelta()`, which 1.20.1 has not. With ~99% of the 1.20.x population on 1.20.1, the user's decision (2026-09-23) is to build this branch on 1.20.1 and leave 1.20.2–1.20.4 on the published `fishingrodfix-1.20-1.20.4-v0.5.jar`; a 1.20.2–1.20.4 target would be a small delta from this branch, not a redesign. The jar-name label `1.20-1.20.1` is hardcoded in `build.gradle`'s `remapJar` block for that reason, instead of reading `minecraft_version`.

## Roles

Project roles:

- `/port-version <mc_version>` — ports the mod (the current reference fix from the default branch) to a target Minecraft version, backport or forward-port. It reviews the port in rounds with `/reviewer` (correctness and performance per round, compatibility once in parallel) until no real bug is left, fixes the rest, and only then launches the game. See `.claude/skills/port-version/SKILL.md`.
- `/reviewer [scope] [--only <dimensions>] [notes]` — read-only, one-pass review of the branch's unpublished changes (or a range, paths, or `all`). Fresh reviewer agents check the default review, a performance gate (the mod's cost within noise of zero on a whole frame's budget) and compatibility with known mods, shader packs and resource packs; the findings are verified and returned as one report. It never edits, builds or commits. See `.claude/skills/reviewer/SKILL.md`.
