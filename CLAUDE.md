# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A client-side Fabric mod for Minecraft that fixes vanilla bugs where the fishing line starts in the wrong place. In first person the line origin is placed on the rod the hand pass actually draws, at vanilla's own attachment point by the tip: across aspect ratios, world and hand FOV, the rod's equip dip, swing and sway, view bob, hurt tilt and nausea warp, the camera's smoothed eye height, and resource packs that redraw the rod. On a player's body (third person, other players, sleeping in any view) it is placed on the tip of the rod the body is drawn holding, in whatever pose the model is in.

Each Minecraft version lives on its own branch and the code differs per version family (see Versioning). This branch targets **MC 1.21.11** (obfuscated: yarn mappings, remapped by Loom; the jar declares `>=1.21.11 <=1.21.11`, closed on purpose: `~1.21.11` means `>=1.21.11 <1.22`, which would also admit the next release and its snapshots (Fabric normalises those as pre-releases of the release they lead to), and the mod's required injectors would crash a client there rather than the loader refusing the mod; the fix reads APIs that 1.21.11 added, such as `ItemStack.getSwingAnimation`, which came with its spears).

## Build Commands

```bash
# Build the mod (produces JARs in build/libs/)
./gradlew build

# Run the Minecraft client with the mod loaded
./gradlew runClient

# Generate sources and set up IDE
./gradlew genSources
```

CI builds with Java 21 (`release 21`); `gradle/gradle-daemon-jvm.properties` makes Gradle run on a JDK 21 for this branch (Loom 1.18+ would need Gradle on JDK 25, so the branch stays on Loom 1.17).

## Architecture (1.21.11)

Purely client-side; no access widener and no Fabric API dependency, and MixinExtras is not bundled either: the loader floor `>=0.15.10` is set by the `JAVA_21` compatibility level — Fabric Loader 0.15.10 is the first that bundles a sponge-mixin whose `CompatibilityLevel` enum has `JAVA_21` at all (0.13.3; the constant arrived in sponge-mixin 0.13.0, but no loader ever shipped 0.13.0–0.13.2, and 0.15.9 bundles 0.12.5, which stops at `JAVA_18`), and an unknown level is a startup `MixinInitialisationError`, not a warning — and every loader from 0.15.7 on already bundles a MixinExtras with `injector.v2.WrapWithCondition`, so a Jar-in-Jar copy would lower nothing. Nor is `>=0.15.10` restrictive, though the margin is one patch: it predates MC 1.21 by two months (2024-04-12 against 2024-06-13), and the lowest loader any Fabulously Optimized pack on the 1.21 line pins is 0.15.11 — its MC 1.21 pack, a version the 1.21.1 branch's `depends.minecraft` covers; the rest are 0.16.7 or newer. (The 1.20 branch, at `JAVA_17`, does bundle MixinExtras — there it drops the floor from `>=0.15.7` to `>=0.14.25`.) Loom remaps the mixins' targets to intermediary itself (no refmap).

- **`FishingBobberEntityRendererMixin`** (`src/client/java/.../mixin/client/`) — `@ModifyExpressionValue` (`allow = 1`) on the only `Vec3d.add(Vec3d)` in `FishingBobberEntityRenderer.getHandPos`, i.e. the result of vanilla's first-person branch: delegates to `FishingLineOrigin`, or keeps vanilla's value while vanilla draws the player's own body (asleep, or a third-person camera on the player in first person), whose rod `ThirdPersonLineOrigin` takes. Where `FishingLineOrigin` keeps vanilla's value with the camera on the player, it tells `ThirdPersonLineOrigin` (a flag reset at `updateRenderState` HEAD), whose line then only moves onto a body drawn earlier in the same pass. The third-person branch isn't hooked: players other mods send down it (First Person Model, Real Camera) get the body-held rod too. It also holds the line-visibility injectors (`updateRenderState` HEAD and TAIL, `@WrapWithCondition` in `render`) and the body-held line's placement at `render` (`require = 0`): a HEAD inject that works the offset out and three `@ModifyVariable`s at the STORE of `render`'s float locals 0–2 (`f`/`g`/`h`) that write it, so nothing is allocated and the state's `pos` keeps vanilla's value.
- **`FishingLineOrigin`** — replaces vanilla's guess (it doesn't reuse vanilla's eye-based vector): reads what this frame's hand pass will draw with (on 1.21.11 `HeldItemRenderer.renderItem` runs from `GameRenderer.renderHand` at the end of `renderWorld`, after the world's entities are extracted, and reads the live player and the renderer's own drawn items and equip progress, `HeldItemRendererAccessor`, at the frame's tick progress; nothing ticks in between, so the same reads during extraction match; its package-private `getHandRenderType` is mirrored), takes the rod's line attachment point from `FirstPersonRod`, applies vanilla's item sway and own view bob/hurt tilt (`GameRendererInvoker`), and places the world point, relative to the camera and with the world-only nausea/portal warp undone (its spin through `GameRendererAccessor`), on the pixel where the hand pass draws that point. Both FOVs are the ones `renderWorld` gets from vanilla's own `GameRenderer.getFov`, so zoom mods that hook it are followed: `GameRendererMixin` captures its two calls (optional `@ModifyExpressionValue`s), the world FOV before the entities are extracted (this frame's) and the hand FOV after them (last frame's, used while the world FOV's factor on top of its options-FOV-times-movement-modifier base is unchanged within float noise: that factor holds the death and fluid factors, which the hand FOV shares, and any zoom a mod multiplies in; so sprinting, speed and flying don't count; otherwise, or without the captures, `getFov` is asked through `GameRendererInvoker`: each call probes the camera's surroundings for fluid, `Camera.getSubmersionType`, a dozen world lookups and ~1 KB of garbage); 1.21.11 keeps no copy of the world projection without the bob and warp, so a mod that changes the projection itself isn't. The rod's hand comes from the drawn items; while a rod is held but none is drawn yet (a quick F-swap with a hook out) the line stays with the hand it was last drawn in. None of its inputs change within a frame (the player and the renderer's fields only in ticks, the camera once per frame), so the origin is worked out once per `HandPass` frame and reused by later extractions of the local player's hooks in it (Iris' shadow pass extracts them first, inside `WorldRenderer.render` before the world's own extraction and its hand pass; nothing it reads changes in between); a panorama capture, which renders the world without a frame of its own, is checked before that reuse. Its class Javadoc lists the steps and every case that keeps vanilla's value.
- **`FirstPersonRod`** — vanilla's first-person rod geometry. The attachment point is vanilla's screen anchor `(±0.525, -0.1)` back-projected, at the 70° hand and an assumed 16:9 calibration aspect, onto the resting rod's model mid-plane, shifted by the pack's tip delta (`RodSprite`), then carried through `applyEquipOffset` (incl. the equip dip), `swingArm`/`applySwingOffset` and the `handheld_rod` display transform.
- **`ThirdPersonLineOrigin`** + `HeldItemFeatureRendererMixin` / `AbstractClientPlayerEntityMixin` — the line origin on a rod held by a player's body, for every line not on the first-person rod: vanilla's third-person branch for every player (MC-4490 crouch, MC-176514 riding, MC-198777 boat, MC-247425 arm swing, MC-270173 swim/crawl, MC-270174 sleep; also walking, gliding, riptide, death), and the local player whose body is drawn in first person (asleep, a mod's third-person camera, a mod drawing it such as Player Animation Library's first-person model mode). Vanilla's third-person value is a fixed offset from the eye turned by the entity's body yaw. Nothing of the pose is modelled: the rod is read where it is drawn. `HeldItemFeatureRendererMixin` (`require = 0`, priority 1500 so it runs after other mods' same-call `@Inject`s, e.g. Player Animation Library's and Animatium's item transforms) sits at `HeldItemFeatureRenderer.renderItem`'s `ItemRenderState.render` call, past its empty check, so once per non-empty held item of an armed entity: a small inlined gate (a body-held hook was extracted this `HandPass` frame, the state is a `PlayerEntityRenderState`, the stack a rod) leads to the out-of-line read, which for the `getArmHoldingRod` rod of a player who is fishing (entity by `id`, `PlayerEntity.fishHook` is set on the client) stores on the player (`AbstractClientPlayerEntityMixin`) the attachment point under the submitted pose, tagged with the pass (queue + frame + the count of queue clears so far: on 1.21.11 one `OrderedRenderCommandQueueImpl`, the `GameRenderer`'s, serves every vanilla pass, the world and its particles, the first-person hand, the screen effects, and the GUI's pictures such as the inventory's player model and its item atlas (each newly shown item, and every animated or glinting one each frame), each cleared once drawn by `RenderDispatcher.render`, so `OrderedRenderCommandQueueImplMixin` counts `OrderedRenderCommandQueueImpl.clear` and a clear ends a pass; while that optional hook doesn't apply, a rod drawn after its hook isn't remembered). The owner, its partial tick and the same-pass-only flag ride on the hook's render state (set at `updateRenderState` TAIL, dropped at its `render`: other mods keep render states past their frame, as Iris' shadow pass keeps its last frame's, also after a disconnect, and the owner would keep its world alive); the pending offset is cleared once `h` is written and the last hook's pass (its queue) at the next frame's start (`GameRendererMixin`), so no static reference outlives its submission or frame. At the hook's `render` HEAD, when the owner's rod was drawn earlier in the same pass (entities submit in the client's add order, owner before the hooks it casts), the line offset is that point through the inverse of the hook's pose (a pass that turns its root cancels out), minus the line's 0.25 lift. Otherwise it is the tip where the rod was last drawn, relative to the body's position and turned with its yaw (`LivingEntityRenderer.clampBodyYaw` mirrored), while the owner still holds a rod in that arm and is in the same pose and riding state; else vanilla's value. A first-person line `FishingLineOrigin` left at vanilla's value (see its Javadoc) with the camera on the player takes only the same-pass rod, never the remembered one: no body is on screen, and the remembered spot (from an F5 view just left, or from Iris' shadow pass, whose entity extraction doesn't skip the camera entity as `WorldRenderer.fillEntityRenderStates` does and so draws the local body with its rod, then the hook) would start the visible line at a rod that isn't drawn. The shadow's own line still sits on the shadow body's rod, and Player Animation Library's first-person body (drawn earlier in the world pass) still carries the line. With the camera on another entity vanilla never draws the local player, so a drawn body is a mod's and may come after the hooks (Freecam's Show Player adds it after the entity extraction): that line keeps the remembered spot, as Real Camera's classic mode does. The remembered offset is taken whenever a hook of the pass gives the world position (also for a rod drawn after its hook, as Real Camera's classic mode does). Exceptions disable it until the next world; without frame counting nothing is read.
- **`ThirdPersonRod`** — the body-held rod's attachment point in the space `HeldItemFeatureRenderer` submits the item in: the rod's tip (`RodSprite`; not first person's vanilla anchor, which sits by the tip only at first-person scale and angle) on the model mid-plane, through the `handheld_rod` `thirdperson_righthand` display transform (the left hand's is the same after `Transformation.apply`'s left-hand fix). Cached per frame.
- **`RodSprite`** — the tip of the `item/fishing_rod_cast` sprite, the rod model's source in every view: a resource pack's redrawn sprite is measured (visible pixels at/above the item alpha cutout, unioned over animation frames; a shift beyond `MAX_TIP_SHIFT`, the measurement's one tuned constant, is ignored as a misread; the scan only covers the sprite's top-right corner, where a usable tip can be, and a sheet too large to measure inside a frame's budget keeps vanilla's tip), cached per `SpriteContents` identity, i.e. per resource reload.
- **`FishingLineVisibility`** + `FishingBobberEntityStateMixin` / `FishingBobberEntityMixin` — hides the line (not the bobber) of a hook whose rod has left its owner's hands, in every perspective and for every player (MC-310980, MC-211561): the server removes such a hook only a tick plus the ping later, or never while the tick rate is frozen. Where `FishingLineOrigin` placed the line on the drawn first-person rod, it stays until the lowering rod is gone from the drawn items (a first-person line left at vanilla's value hides at once: vanilla would start it at the off-hand side, where no rod is). Only hooks whose owner was seen holding a rod (a flag on the hook) are hidden, so hooks cast by other items keep vanilla's line; for the local player a rod among the drawn items counts too (the own hook arrives a round trip after the cast). Decided at the end of `updateRenderState`, carried on the render state, applied by a `@WrapWithCondition` (MixinExtras v2) that skips the `RenderLayers.lines()` `submitCustom` in `render`; an exception leaves lines visible until the next world or dimension.
- **`HandPass`** + `GameRendererMixin` / `HeldItemRendererMixin` — whether the hand pass reached a hand last frame (frames counted where `GameRenderer.render` calls `updateCamera`, i.e. once per rendered frame: past its `skipGameRender` check, through which Dynamic FPS skips most frames while throttling (a skipped frame counted as one without a hand would put the line at vanilla's value), the frame marked where the five-argument `HeldItemRenderer.renderItem` calls `renderFirstPersonItem`, past any cancel; also reached while scoping, where nothing is drawn, so `FishingLineOrigin` checks scoping itself). No rod on screen → vanilla's value, whatever hid the hand (spectator, a mod cancelling the hand pass), unless the player's own body is drawn with the rod in the world pass (asleep, a third-person camera; Player Animation Library's first-person model mode, whose body counts only when drawn earlier in the same pass than the hook): then `ThirdPersonLineOrigin` puts the line on that rod. The HUD hidden with F1 is the exception: it hides the hand but not the line, a world object, so the line stays corrected where the rod would be. The frame counter runs before the camera update, so at each frame's `renderWorld` HEAD (after the tick and the camera update, before the entities and the hand pass) `HandPass` samples the live `GameOptions.hudHidden` (which `renderHand` reads later in the frame) and the rest of `renderHand`'s gate (first person, not rendering a panorama, awake, not spectating), plus the camera on the player, not in third person and at the player's eye where `Camera.update` puts it (some freecam mods keep the player as camera entity and don't move the camera into third person; the smoothed eye height comes through `CameraAccessor`). At the next frame's start it latches whether a hand is drawn when only the HUD decides, from frames that prove it (a drawn hand; a missing one with the HUD and the gate open means a mod hid it); a frame with the gate closed, or one that didn't render the world, restores the default (drawn). While the HUD is hidden (this or the previous frame) the line stays corrected if that latch holds and the gate is open this frame. So a hidden HUD never moves the line (Camerapture's photo frame and freecams on their own camera entity keep vanilla's value, unless they draw the player's body, as Freecam's Show Player, its default, does: then the body's rod, one frame late, from the remembered spot; freecams that move the player's camera into third person keep the body's rod; F5, sleep or spectator before F1 don't stick). Mods that keep the hand while hiding the HUD (Better F1) stay corrected through the normal path. These injects are `require = 0`: if the counter or the mark is blocked, the line just stays vanilla, and `FishingLineOrigin` logs one warning (frame counter never ran, or no hand mark seen while fishing in first person); without the sampling, F1 leaves vanilla's line.
- **`SpriteContentsAccessor`** — `@Accessor` for `SpriteContents.image`. **`CameraAccessor`** — `@Accessor`s for `Camera.cameraY`/`lastCameraY`. **`GameRendererInvoker`** — `@Invoker`s for `GameRenderer.tiltViewWhenHurt`/`bobView`/`getFov`. **`GameRendererAccessor`** — `@Accessor`s for `GameRenderer.nauseaEffectTime`/`nauseaEffectSpeed` (the warp's spin) and `fovMultiplier`/`lastFovMultiplier` (the movement FOV modifier, for the shared FOV factor). **`HeldItemRendererAccessor`** — `@Accessor`s for `HeldItemRenderer`'s drawn items and equip progress. **`OrderedRenderCommandQueueImplMixin`** — counts `OrderedRenderCommandQueueImpl.clear` calls for `ThirdPersonLineOrigin`'s pass tag (`@ModifyExpressionValue`, `require = 0`, on the method's only field read, so nothing is allocated). **`FishingRodFix`** — the shared logger, `isRod` and `holdsRod`.

Declared incompatible: Enchanted Fishing Line (`enchanted_fishing_line`, all versions) is listed under `breaks` in `fabric.mod.json`, so the loader refuses to start with both and shows its incompatible-mods screen. Its builds (1.0.0 for 26.2 and 26.1–26.1.2, 1.0.0-hotfix for 1.21.11) carry a copy of this mod's v0.5 correction as a cancellable `@Inject(RETURN)` on the hand-position method (`getHandPos` here) with no check for this mod. v0.5's own RETURN inject cancelled first, so only one correction applied; v0.6's first-person hook sits inside the method and can't pre-empt it, so EFL's copy stacked on the corrected origin (off the rod on windows other than 16:9, with FOV modifiers, while turning and crouching), and its rope, drawn by its own call from the state's line origin, got neither the body-held offset nor the line hiding. User decision 2026-09-22: `breaks` on every branch, no EFL-specific code.

Known limitations: per-item model swaps (server `custom_model_data`/`item_model`, CIT), 3D rod models and changed display transforms are not measured; mods that re-pose the hand in the renderer without touching the state it reads (viewmodel mods such as Punchy, ViewModel, ScaleMe, Smallhands, Animatium's legacy item positions and 1.7/1.8 fishing rod (whose own shift of vanilla's line the correction replaces), Mine Little Pony's first-person unicorn magic, CameraTweaks' first-person freelook, Inspect Animations), shaderpack hand sway, portal-view mods that move the camera (Immersive Portals), Polytone line offsets and Tide's own hook renderer are not covered; on 1.21.11 the hand pass reads the live player and its renderer's fields, and its hand selection (`HeldItemRenderer.getHandRenderType`) is mirrored, not read, so a mod that changes `renderItem`'s locals or arguments (swing, sway, equip dip, the drawn item: Animatium's equip animation hands the main-hand call its own stack in its 1.7/1.8 modes) or that selection isn't followed (a hand it hides keeps the line at the hidden rod; one it draws where vanilla wouldn't keeps vanilla's value), while mods that change the renderer's fields (Player Animation Library's and Animatium's equip changes in `updateHeldItems`) are; the world FOV is `getFov`'s, so mods that change the world projection itself rather than `getFov` (an orthographic camera, a lens) aren't followed, nor, reliably, Zoomify's "Affect Hand FOV" turned off (not its default), which zooms the hand back at `renderWorld`'s call rather than in `getFov`: the line can be off the rod while zoomed (always during zoom changes and with an Iris shader pack), as vanilla's is; mods that bob or sway the hand and world passes differently (BetterHandBobbing, View Bobbing Options, No Screen Bobbing, Tweakeroo's world view-bob toggle, Animatium's Minimal View Bobbing, ShakeTweaks' bob toggles and "Disable Hand View Sway"), and Clearviews with "Disable Nausea" turned off, leave the same mismatch vanilla has; mods that drop the nausea warp without Clearviews' mod id (anti-nausea in Meteor, Wurst, LiquidBounce) make the line swing around the rod under nausea/portal — Clearviews itself doesn't collide with Iris shaders here: it has no build for this version (its newest on the 1.21 line is 2.0.6, for 1.21.6–1.21.8, where Iris redirects other instructions and, with a pack on, zeroes the warp intensity so Clearviews' wrappers never run); mods that hide one arm by cancelling its `renderFirstPersonItem` (Hide Hands, Exposure, Tweakeroo's Disable Offhand Rendering), or only its item (Player Animation Library during a first-person transition), leave the line at the hidden rod's tip, as do mods that hide the hand only after F1 was pressed (Camerapture's camera, Snapmatica's viewfinder, Picture Mode); conversely a mod that stops hiding the hand while F1 is on (Snapmatica's viewfinder or a freecam parked at the eye) leaves vanilla's line until F1 is released; camera-smoothing mods (SmoothCamera) drop the F1 line to vanilla's value during their F5/teleport glide; a local cast followed by a slot switch before the hook reaches the client, on a ping longer than the drawn items' few-tick lag, keeps vanilla's line until the server removes the hook. On a player's body (third person): the rod is read where `HeldItemFeatureRenderer` submits it, so everything that poses the body, arm or item before that call is followed (animation mods, held-item position mods, First Person Model's offset body, Mine Little Pony's ponies), but not what changes the item after it (a resource pack's changed `thirdperson` display transform, per-item or 3D rod models, Animatium's 1.7 stick rod, a wrap, redirect or argument change of that call, or a same-call `@Inject` above priority 1500), nor rods drawn outside the world pass's queue (Real Camera's default binding mode, Mine Little Pony's magic ponies with third-person magic) or not through that feature renderer (morph mods such as Woodwalkers: vanilla's value). Mine Little Pony's magic keeps vanilla's or Mine Little Pony's value; Real Camera's binding mode draws the body into its own queue after the hooks, so its line starts where the body's rod was last drawn in a pass with its hook (every frame with Iris entity shadows, whose shadow pass draws the same body and hook; else an earlier F5 view), under the rules below, and keeps vanilla's value until then. Likewise Freecam with Show Player off (its own camera entity, the body hidden) can start the line where the hidden body's rod was last drawn (an F5 view; Freecam keeps the hidden body out of Iris' shadow pass too) while the pose matches. Where the owner's rod isn't drawn in the pass before its hook (the owner out of view, a hook that arrived before its owner, a body drawn after the hooks), the line starts where it was last drawn, turned with the body (except a reading taken asleep, which is in the bed's space: vanilla turns a sleeping body by the bed's direction, not by the body yaw, so that reading is used unturned), while the pose and riding state match; a changed arm pose (a swing) shows when the rod is drawn again, and a player never seen with the rod drawn, or in another pose since, keeps vanilla's value until it is (a jump then); a player who starts drawing another way in the same pose while fishing (a morph mid-cast) keeps that remembered spot. A remembered spot is relative to the body's position, so it also carries the offset the reading frame drew the body at (`PlayerEntityRenderer.getPositionOffset`): the crouch shift, which the pose gate keeps in step, and, for a passenger of an experimental-movement minecart, that frame's cart lerp correction, a fraction of a block until the rod is drawn again. A rod hidden by another mod (Not Enough Animations' off-hand hiding) leaves the line where the rod was last drawn; hidden in bed (its default) the line keeps vanilla's value unless the rod was seen drawn in bed before. The state's `pos` keeps vanilla's value for a body-held rod, so a mod that reads it sees that. A mod rendering the world twice per frame into one queue without clearing it in between could hand one pass's rod to the other (vanilla's passes each end with a clear, which ends a pass here).

## Dev environment gotcha

Loom writes `.idea/runConfigurations/Minecraft_Client.xml` only when it is missing and never updates it, and `.idea` is shared by every branch of the checkout. A stale config on the 26.3 branch lacks `-XX:StackShadowPages=32` (from Mojang's version JSON), and the client then dies natively on an in-world resource reload (access violation in `jvm.dll`, no `hs_err`). A 26.x config on an old branch fails to start on JDK 21 (`--sun-misc-unsafe-memory-access`). After switching version families, delete the XML and run `./gradlew ideaSyncTask`.

## Versioning

Each Minecraft version lives on its own branch (e.g. `1.21.4`, `1.21.11`, `26.3`). The version numbers in `gradle.properties` (`minecraft_version`, `loader_version`, `loom_version` — on branches not yet ported to the current fix the Loom version sits in `build.gradle`'s `plugins` block instead — and `yarn_mappings` on pre-26 branches) must be updated together when porting to a new MC version. The `mod_version` in `gradle.properties` is independent of MC version.

## Roles

Project roles:

- `/port-version <mc_version>` — ports the mod (the current reference fix from the default branch) to a target Minecraft version, backport or forward-port. It reviews the port in rounds with `/reviewer` (correctness and performance per round, compatibility once in parallel) until no real bug is left, fixes the rest, and only then launches the game. See `.claude/skills/port-version/SKILL.md`.
- `/reviewer [scope] [--only <dimensions>] [notes]` — read-only, one-pass review of the branch's unpublished changes (or a range, paths, or `all`). Fresh reviewer agents check the default review, a performance gate (the mod's cost within noise of zero on a whole frame's budget) and compatibility with known mods, shader packs and resource packs; the findings are verified and returned as one report. It never edits, builds or commits. See `.claude/skills/reviewer/SKILL.md`.
