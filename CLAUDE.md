# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A client-side Fabric mod for Minecraft that fixes vanilla bugs where the fishing line starts in the wrong place. In first person the line origin is placed on the rod the hand pass actually draws, at vanilla's own attachment point by the tip: across aspect ratios, world and hand FOV, the rod's equip dip, swing and sway, view bob, hurt tilt and nausea warp, the camera's smoothed eye height, and resource packs that redraw the rod. On a player's body (third person, other players, sleeping in any view) it is placed on the tip of the rod the body is drawn holding, in whatever pose the model is in.

Each Minecraft version lives on its own branch and the code differs per version family (see Versioning). This branch targets **MC 26.2** (unobfuscated, official Mojang names).

## Build Commands

```bash
# Build the mod (produces JARs in build/libs/)
./gradlew build

# Run the Minecraft client with the mod loaded
./gradlew runClient

# Generate sources and set up IDE
./gradlew genSources
```

CI builds with Java 25 (`release 25`); run Gradle on a JDK 25 for 26.x branches.

## Architecture (26.2)

Purely client-side; no access widener and no Fabric API dependency, and MixinExtras is not bundled either: the loader's own copy has `injector.v2.WrapWithCondition` from 0.15.7 on, and the `JAVA_25` compatibility level needs sponge-mixin 0.16+ (Fabric Loader 0.17.0) — both far under the declared floor `>=0.19.0`. That floor is therefore above the minimum that merely *loads* — measured on 26.3: with the floor hand-lowered, the jar runs on Fabric Loader 0.18.6 and 0.17.2 with all ten mixins applying — and it is kept where it is on purpose, because `depends.fabricloader` also picks the Mixin behaviour set the loader applies to this mod (`FabricMixinVersions` on loader 0.19.5 — older loaders carry fewer rows: `>=0.19.4` → 0.17.4, `>=0.19.0` → 0.17.1, `>=0.18.4` → 0.17.0, `>=0.17.3` → 0.16.5, `>=0.16.0` → 0.14.0, `>=0.12.0` → 0.10.0): below Fabric compat 0.17.1 a mixin's injectors are prepared through `INJECT_PREPARE_LEGACY`, so lowering the floor is a behavioural change, not a metadata tweak. Nothing is asking for it on this line either: Fabulously Optimized for this MC version pins Fabric Loader 0.19.5. A Jar-in-Jar MixinExtras copy would lower nothing. (The 1.20 branch, at `JAVA_17`, does bundle MixinExtras — there it drops the floor from `>=0.15.7` to `>=0.14.25`.)

- **`FishingHookRendererMixin`** (`src/client/java/.../mixin/client/`) — `@ModifyExpressionValue` (`allow = 1`) on the only `Vec3.add(Vec3)` in `FishingHookRenderer.getPlayerHandPos`, i.e. the result of vanilla's first-person branch: delegates to `FishingLineOrigin`, or keeps vanilla's value while vanilla draws the player's own body (asleep, or a detached camera), whose rod `ThirdPersonLineOrigin` takes. Where `FishingLineOrigin` keeps vanilla's value with the camera on the player, it tells `ThirdPersonLineOrigin` (a flag reset at `extractRenderState` HEAD), whose line then only moves onto a body drawn earlier in the same pass. The third-person branch isn't hooked: players other mods send down it (First Person Model, Real Camera) get the body-held rod too. It also holds the line-visibility injectors (`extractRenderState` HEAD and TAIL, `@WrapWithCondition` in `submit`) and the body-held line's placement at `submit` (`require = 0`): a HEAD inject that works the offset out and three `@ModifyVariable`s at the STORE of `submit`'s float locals 0–2 (`xa`/`ya`/`za`) that write it, so nothing is allocated and `lineOriginOffset` keeps vanilla's value.
- **`FishingLineOrigin`** — replaces vanilla's guess (it doesn't reuse vanilla's eye-based vector): reads what this frame's hand pass will draw with (on 26.2 `ItemInHandRenderer.submitHandsWithItems` runs from `renderLevel` after extraction and reads the live player and the renderer's own drawn items and equip heights, `ItemInHandRendererAccessor`, at the camera entity's partial tick; nothing ticks in between, so the same reads during extraction match; its package-private `evaluateWhichHandsToRender` is mirrored), takes the rod's line attachment point from `FirstPersonRod`, applies vanilla's item sway and own view bob/hurt tilt (`GameRendererInvoker`), and places the world point, relative to the camera and with the world-only nausea/portal warp undone (its spin through `GameRendererAccessor`), on the pixel where the hand pass draws that point. The world FOV comes from the extracted world projection's `m11` (in vanilla the camera's FOV), so mods that change the projection itself are followed too; an orthographic projection keeps vanilla's value. The rod's hand comes from the drawn items; while a rod is held but none is drawn yet (a quick F-swap with a hook out) the line stays with the hand it was last drawn in. None of its inputs change within a frame (the player and the renderer's fields only in ticks, the camera and the extracted states once per frame), so the origin is worked out once per `HandPass` frame and reused by later extractions of the local player's hooks in it (Iris' shadow pass extracts them again, before its hand pass). Its class Javadoc lists the steps and every case that keeps vanilla's value.
- **`FirstPersonRod`** — vanilla's first-person rod geometry. The attachment point is vanilla's screen anchor `(±0.525, -0.1)` back-projected, at the 70° hand and an assumed 16:9 calibration aspect, onto the resting rod's model mid-plane, shifted by the pack's tip delta (`RodSprite`), then carried through `applyItemArmTransform` (incl. the equip dip), `swingArm` and the `handheld_rod` display transform.
- **`ThirdPersonLineOrigin`** + `ItemInHandLayerMixin` / `AbstractClientPlayerMixin` — the line origin on a rod held by a player's body, for every line not on the first-person rod: vanilla's third-person branch for every player (MC-4490 crouch, MC-176514 riding, MC-198777 boat, MC-247425 arm swing, MC-270173 swim/crawl, MC-270174 sleep; also walking, gliding, riptide, death), and the local player whose body is drawn in first person (asleep, a mod-detached camera, a mod drawing it such as Player Animation Library's first-person model mode). Vanilla's third-person value is a fixed offset from the eye turned by the entity's body yaw. Nothing of the pose is modelled: the rod is read where it is drawn. `ItemInHandLayerMixin` (`require = 0`, priority 1500 so it runs after other mods' same-call `@Inject`s, e.g. Player Animation Library's and Animatium's item transforms) sits at `ItemInHandLayer.submitArmWithItem`'s `ItemStackRenderState.submit` call, past its empty check, so once per non-empty held item of an armed entity: a small inlined gate (a body-held hook was extracted this `HandPass` frame, the state is an `AvatarRenderState`, the stack a rod) leads to the out-of-line read, which for the `getHoldingArm` rod of a player who is fishing (entity by `id`, `Player.fishing` is set on the client) stores on the player (`AbstractClientPlayerMixin`) the attachment point under the submitted pose, tagged with the pass (collector + frame; valid while a collector serves one pass per frame, as vanilla's level pass, its picture-in-picture renderers and Iris' shadow pass each do with their own storage). The owner, its partial tick and the same-pass-only flag ride on the hook's render state (set at `extractRenderState` TAIL, dropped at its `submit`: other mods keep render states past their frame, as Iris' shadow pass keeps its last frame's, also after a disconnect, and the owner would keep its world alive); the pending offset is cleared once `za` is written and the last hook's pass (its collector) at the next frame's start (`GameRendererMixin`), so no static reference outlives its submit or frame. At the hook's `submit` HEAD, when the owner's rod was drawn earlier in the same pass (entities submit in the client's add order, owner before the hooks it casts), the line offset is that point through the inverse of the hook's pose (a pass that turns its root cancels out), minus the line's 0.25 lift. Otherwise it is the tip where the rod was last drawn, relative to the body's position and turned with its yaw (`solveBodyRot` mirrored), while the owner still holds a rod in that arm and is in the same pose and riding state; else vanilla's value. A first-person line `FishingLineOrigin` left at vanilla's value (see its Javadoc) with the camera on the player takes only the same-pass rod, never the remembered one: no body is on screen, and the remembered spot (from an F5 view just left, or from Iris' shadow pass, whose entity extraction doesn't skip the camera entity as `LevelExtractor.extractVisibleEntities` does and so draws the local body with its rod, then the hook) would start the visible line at a rod that isn't drawn. The shadow's own line still sits on the shadow body's rod, and Player Animation Library's first-person body (drawn earlier in the level pass) still carries the line. With the camera on another entity vanilla never draws the local player, so a drawn body is a mod's and may come after the hooks (Freecam's Show Player adds it at `extractVisibleEntities` RETURN): that line keeps the remembered spot, as Real Camera's classic mode does. The remembered offset is taken whenever a hook of the pass gives the world position (also for a rod drawn after its hook, as Real Camera's classic mode does). Exceptions disable it until the next world; without frame counting nothing is read.
- **`ThirdPersonRod`** — the body-held rod's attachment point in the space `ItemInHandLayer` submits the item in: the rod's tip (`RodSprite`; not first person's vanilla anchor, which sits by the tip only at first-person scale and angle) on the model mid-plane, through the `handheld_rod` `thirdperson_righthand` display transform (the left hand's is the same after `ItemTransform.apply`'s left-hand fix). Cached per frame.
- **`RodSprite`** — the tip of the `item/fishing_rod_cast` sprite, the rod model's source in every view: a resource pack's redrawn sprite is measured (visible pixels at/above the item alpha cutout, unioned over animation frames; a shift beyond `MAX_TIP_SHIFT`, the measurement's one tuned constant, is ignored as a misread; the scan only covers the sprite's top-right corner, where a usable tip can be, and a sheet too large to measure inside a frame's budget keeps vanilla's tip), cached per `SpriteContents` identity, i.e. per resource reload.
- **`FishingLineVisibility`** + `FishingHookRenderStateMixin` / `FishingHookMixin` — hides the line (not the bobber) of a hook whose rod has left its owner's hands, in every perspective and for every player (MC-310980, MC-211561): the server removes such a hook only a tick plus the ping later, or never while the tick rate is frozen. Where `FishingLineOrigin` placed the line on the drawn first-person rod, it stays until the lowering rod is gone from the drawn items (a first-person line left at vanilla's value hides at once: vanilla would start it at the off-hand side, where no rod is). Only hooks whose owner was seen holding a rod (a flag on the hook) are hidden, so hooks cast by other items keep vanilla's line; for the local player a rod among the drawn items counts too (the own hook arrives a round trip after the cast). Decided at the end of `extractRenderState`, carried on the render state, applied by a `@WrapWithCondition` (MixinExtras v2) that skips the `lines` geometry in `submit`; an exception leaves lines visible until the next world or dimension.
- **`HandPass`** + `GameRendererMixin` / `ItemInHandRendererMixin` — whether the hand pass reached a hand last frame (frames counted at `GameRenderer.extract`, the frame marked where `submitHandsWithItems` calls `submitArmWithItem`, past any cancel; also reached while scoping, where nothing is drawn, so `FishingLineOrigin` checks scoping itself). No rod on screen → vanilla's value, whatever hid the hand (spectator, a mod cancelling the hand pass), unless the player's own body is drawn with the rod in the level pass (asleep, a detached camera; Player Animation Library's first-person model mode, whose body counts only when drawn earlier in the same pass than the hook): then `ThirdPersonLineOrigin` puts the line on that rod. The HUD hidden with F1 is the exception: it hides the hand but not the line, a world object, so the line stays corrected where the rod would be. At each frame's `extract` (after the tick and the camera update) `HandPass` samples the live `Hud.isHidden()` and the rest of `renderItemInHand`'s gate (first person, not panoramic, awake, not spectating), plus the camera on the player, not detached and at the player's eye where `Camera.alignWithEntity` puts it (some freecam mods keep the player as camera entity and don't detach; the smoothed eye height comes through `CameraAccessor`). It latches whether a hand is drawn when only the HUD decides, from frames that prove it (a drawn hand; a missing one with the HUD and the gate open means a mod hid it); a frame with the gate closed restores the default (drawn). While the HUD is hidden (this or the previous frame) the line stays corrected if that latch holds and the gate is open this frame. So a hidden HUD never moves the line (Camerapture's photo frame and freecams on their own camera entity keep vanilla's value, unless they draw the player's body, as Freecam's Show Player, its default, does: then the body's rod, one frame late, from the remembered spot; freecams that detach the camera from the player keep the body's rod; F5, sleep or spectator before F1 don't stick). Mods that keep the hand while hiding the HUD (Better F1) stay corrected through the normal path. Both injects are `require = 0`: if blocked, the line just stays vanilla, and `FishingLineOrigin` logs one warning (frame counter never ran, or no hand mark seen while fishing in first person).
- **`SpriteContentsAccessor`** — `@Accessor` for `SpriteContents.originalImage`. **`CameraAccessor`** — `@Accessor`s for `Camera.eyeHeight`/`eyeHeightOld`. **`GameRendererInvoker`** — `@Invoker`s for `GameRenderer.bobHurt`/`bobView`. **`GameRendererAccessor`** — `@Accessor`s for `GameRenderer.spinningEffectTime`/`spinningEffectSpeed` (the warp's spin). **`ItemInHandRendererAccessor`** — `@Accessor`s for `ItemInHandRenderer`'s drawn items and equip heights. **`FishingRodFix`** — the shared logger, `isRod` and `holdsRod`.

Declared incompatible: Enchanted Fishing Line (`enchanted_fishing_line`, all versions) is listed under `breaks` in `fabric.mod.json`, so the loader refuses to start with both and shows its incompatible-mods screen. Its builds (1.0.0 for 26.2 and 26.1–26.1.2, 1.0.0-hotfix for 1.21.11) carry a copy of this mod's v0.5 correction as a cancellable `@Inject(RETURN)` on `getPlayerHandPos` with no check for this mod. v0.5's own RETURN inject cancelled first, so only one correction applied; v0.6's first-person hook sits inside the method and can't pre-empt it, so EFL's copy stacked on the corrected origin (off the rod on windows other than 16:9, with FOV modifiers, while turning and crouching), and its rope, drawn by its own call from `lineOriginOffset`, got neither the body-held offset nor the line hiding. User decision 2026-09-22: `breaks` on every branch, no EFL-specific code.

Known limitations: per-item model swaps (server `custom_model_data`/`item_model`, CIT), 3D rod models and changed display transforms are not measured; mods that re-pose the hand, or change the item it draws, in the renderer without touching the state it reads (viewmodel mods such as Punchy, ViewModel, ScaleMe, Smallhands, Animatium's legacy item positions, CameraTweaks' first-person freelook, Inspect Animations; the drawn item: Animatium's equip animation, which passes its own main-hand stack to the per-hand call), shaderpack hand sway, portal-view mods that move the camera (Immersive Portals), Polytone line offsets and Tide's own hook renderer are not covered; on 26.2 the hand pass reads the live player and its renderer's fields, and its hand selection (`ItemInHandRenderer.evaluateWhichHandsToRender`) is mirrored, not read, so a mod that changes `submitHandsWithItems`' locals or arguments (swing, sway, equip dip) or that selection isn't followed (a hand it hides keeps the line at the hidden rod; one it draws where vanilla wouldn't keeps vanilla's value), while mods that change the renderer's fields (Player Animation Library's and Animatium's equip changes in `tick`) are; mods that bob or sway the hand and world passes differently (BetterHandBobbing, View Bobbing Options, No Screen Bobbing, Tweakeroo's world view-bob toggle, Animatium's Minimal View Bobbing, ShakeTweaks' bob toggles and "Disable Hand View Sway"), and Clearviews with "Disable Nausea" turned off, leave the same mismatch vanilla has; mods that drop the nausea warp without Clearviews' mod id (anti-nausea in Meteor, Wurst, LiquidBounce), and Clearviews + Iris shaders when Iris' warp wrapper (`MixinModelViewBobbing`, on the same calls Clearviews wraps) wins the load order, make the line swing around the rod under nausea/portal; mods that extract a frame without rendering it (sbsshot's stereo screenshots) leave that shot, and the next frame, with vanilla's line; mods that hide one arm by cancelling its `submitArmWithItem` (Hide Hands, Exposure, Tweakeroo's Disable Offhand Rendering), or only its item (Player Animation Library during a first-person transition), leave the line at the hidden rod's tip, as do mods that hide the hand only after F1 was pressed (Camerapture's camera, Snapmatica's viewfinder, Picture Mode); conversely a mod that stops hiding the hand while F1 is on (Snapmatica's viewfinder or a freecam parked at the eye) leaves vanilla's line until F1 is released; camera-smoothing mods (SmoothCamera) drop the F1 line to vanilla's value during their F5/teleport glide; a local cast followed by a slot switch before the hook reaches the client, on a ping longer than the drawn items' few-tick lag, keeps vanilla's line until the server removes the hook. On a player's body (third person): the rod is read where `ItemInHandLayer` submits it, so everything that poses the body, arm or item before that call is followed (animation mods, held-item position mods, First Person Model's offset body, Mine Little Pony's ponies), but not what changes the item after it (a resource pack's changed `thirdperson` display transform, per-item or 3D rod models, Animatium's 1.7 stick rod, a wrap, redirect or argument change of that call, or a same-call `@Inject` above priority 1500), nor rods drawn outside the level pass's collector (Real Camera's default binding mode, Mine Little Pony's magic ponies with third-person magic) or not through that layer (morph mods such as Woodwalkers: vanilla's value). Mine Little Pony's magic keeps vanilla's or Mine Little Pony's value; Real Camera's binding mode draws the body into its own collector after the hooks, so its line starts where the body's rod was last drawn in a pass with its hook (every frame with Iris entity shadows, whose shadow pass draws the same body and hook; else an earlier F5 view), under the rules below, and keeps vanilla's value until then. Likewise Freecam with Show Player off (its own camera entity, the body hidden) can start the line where the hidden body's rod was last drawn (an F5 view, Iris' shadow pass) while the pose matches. Where the owner's rod isn't drawn in the pass before its hook (the owner out of view, a hook that arrived before its owner, a body drawn after the hooks), the line starts where it was last drawn, turned with the body, while the pose and riding state match; a changed arm pose (a swing) shows when the rod is drawn again, and a player never seen with the rod drawn, or in another pose since, keeps vanilla's value until it is (a jump then); a player who starts drawing another way in the same pose while fishing (a morph mid-cast) keeps that remembered spot. A remembered spot is relative to the body's position, so it also carries the offset the reading frame drew the body at (`AvatarRenderer.getRenderOffset`): the crouch shift, which the pose gate keeps in step, and, for a passenger of an experimental-movement minecart, that frame's cart lerp correction, a fraction of a block until the rod is drawn again. A rod hidden by another mod (Not Enough Animations' off-hand hiding) leaves the line where the rod was last drawn; hidden in bed (its default) the line keeps vanilla's value unless the rod was seen drawn in bed before. `lineOriginOffset` on the hook's render state keeps vanilla's value for a body-held rod, so a mod that reads it sees that. A mod rendering the level twice per frame into one collector (portal mods on older versions) could hand one pass's rod to the other.

## Dev environment gotcha

Loom writes `.idea/runConfigurations/Minecraft_Client.xml` only when it is missing and never updates it, and `.idea` is shared by every branch of the checkout. A stale config on the 26.3 branch lacks `-XX:StackShadowPages=32` (from Mojang's version JSON), and the client then dies natively on an in-world resource reload (access violation in `jvm.dll`, no `hs_err`). A 26.x config on an old branch fails to start on JDK 21 (`--sun-misc-unsafe-memory-access`). After switching version families, delete the XML and run `./gradlew ideaSyncTask`.

## Versioning

Each Minecraft version lives on its own branch (e.g. `1.21.4`, `1.21.11`, `26.3`). The version numbers in `gradle.properties` (`minecraft_version`, `loader_version`, `loom_version` — on pre-26 branches the Loom version sits in `build.gradle`'s `plugins` block instead — and `yarn_mappings` on pre-26 branches) must be updated together when porting to a new MC version. The `mod_version` in `gradle.properties` is independent of MC version.

## Roles

Project roles:

- `/port-version <mc_version>` — ports the mod (the current reference fix from the default branch) to a target Minecraft version, backport or forward-port. It reviews the port in rounds with `/reviewer` (correctness and performance per round, compatibility once in parallel) until no real bug is left, fixes the rest, and only then launches the game. See `.claude/skills/port-version/SKILL.md`.
- `/reviewer [scope] [--only <dimensions>] [notes]` — read-only, one-pass review of the branch's unpublished changes (or a range, paths, or `all`). Fresh reviewer agents check the default review, a performance gate (the mod's cost within noise of zero on a whole frame's budget) and compatibility with known mods, shader packs and resource packs; the findings are verified and returned as one report. It never edits, builds or commits. See `.claude/skills/reviewer/SKILL.md`.
