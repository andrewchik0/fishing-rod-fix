# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A client-side Fabric mod for Minecraft that fixes vanilla bugs where the fishing line starts in the wrong place. In first person the line origin is placed on the rod the hand pass actually draws, at vanilla's own attachment point by the tip: across aspect ratios, world and hand FOV, the rod's equip dip, swing and sway, view bob, hurt tilt and nausea warp, the camera's smoothed eye height, and resource packs that redraw the rod. On a player's body (third person, other players, sleeping in any view) it is placed on the tip of the rod the body is drawn holding, in whatever pose the model is in.

Each Minecraft version lives on its own branch and the code differs per version family (see Versioning). This branch targets **MC 1.21.8** and covers **1.21.6–1.21.8** with one jar (obfuscated: yarn mappings, remapped by Loom; built against 1.21.8, the jar declares `>=1.21.6 <=1.21.8` and is named `fishingrodfix-1.21.6-1.21.8-v<mod_version>.jar`). 1.21.6–1.21.8 draw the line and the held items directly — the deferred render-command queue arrived in 1.21.9 — so the line is a `renderFishingLine` loop in `FishingBobberEntityRenderer.render`, held items go through `HeldItemFeatureRenderer.renderItem`, and every pass of a frame draws into the `GameRenderer`'s one `VertexConsumerProvider.Immediate`. 1.21.11's spears (`ItemStack.getSwingAnimation`, swap-animation scales) and the items atlas (1.21.11) don't exist here; `SpriteContents.isAnimated()` doesn't either. The range is safe by construction (checked 2026-09-22 on the intermediary jars): every class the fix **mixes into**, and every other class whose bytecode it depends on, is byte-identical across 1.21.6, 1.21.7 and 1.21.8 — `FishingBobberEntityRenderer`, `FishingBobberEntity`, `FishingBobberEntityState`, `GameRenderer`, `Camera`, `WorldRenderer`, `EntityRenderDispatcher`, `HeldItemRenderer`, `HeldItemFeatureRenderer`, `VertexConsumerProvider$Immediate`, `SpriteContents`, `BakedModelManager`, `AbstractClientPlayerEntity`, `PlayerEntityRenderState`, `ArmedEntityRenderState` — so every injection point and every bytecode ordinal holds. Of the classes the fix only reads, exactly two changed (`ItemRenderState` and `SpriteAtlasTexture`, both 1.21.6 → 1.21.7) and both kept every member it uses; all 136 Minecraft members the built jar references resolve in all three versions. Same 113 libraries, Java 21 and launcher JVM arguments; `handheld_rod.json` and `fishing_rod_cast.png` identical.

## Build Commands

```bash
# Build the mod (produces JARs in build/libs/)
./gradlew build

# Run the Minecraft client with the mod loaded
./gradlew runClient

# Generate sources and set up IDE
./gradlew genSources
```

CI builds with Java 21 (`release 21`); `gradle/gradle-daemon-jvm.properties` makes Gradle run on a JDK 21 for this branch (Loom 1.18+ would need Gradle on JDK 25, so the branch stays on Loom 1.17).

## Architecture (1.21.8)

Purely client-side; no access widener and no Fabric API dependency, and MixinExtras is not bundled either: the loader floor `>=0.15.10` is set by the `JAVA_21` compatibility level — Fabric Loader 0.15.10 is the first that bundles a sponge-mixin whose `CompatibilityLevel` enum has `JAVA_21` at all (0.13.3; the constant arrived in sponge-mixin 0.13.0, but no loader ever shipped 0.13.0–0.13.2, and 0.15.9 bundles 0.12.5, which stops at `JAVA_18`), and an unknown level is a startup `MixinInitialisationError`, not a warning — and every loader from 0.15.7 on already bundles a MixinExtras with `injector.v2.WrapWithCondition`, so a Jar-in-Jar copy would lower nothing. Nor is `>=0.15.10` restrictive, though the margin is one patch: it predates MC 1.21 by two months (2024-04-12 against 2024-06-13), and the lowest loader any Fabulously Optimized pack on the 1.21 line pins is 0.15.11 — its MC 1.21 pack, a version the 1.21.1 branch's `depends.minecraft` covers; the rest are 0.16.7 or newer. (The 1.20 branch, at `JAVA_17`, does bundle MixinExtras — there it drops the floor from `>=0.15.7` to `>=0.14.25`.) Loom remaps the mixins' targets to intermediary itself (no refmap).

- **`FishingBobberEntityRendererMixin`** (`src/client/java/.../mixin/client/`) — `@ModifyExpressionValue` (`allow = 1`) on the only `Vec3d.add(Vec3d)` in `FishingBobberEntityRenderer.getHandPos`, i.e. the result of vanilla's first-person branch: delegates to `FishingLineOrigin`, or keeps vanilla's value while vanilla draws the player's own body (asleep, or a third-person camera on the player in first person), whose rod `ThirdPersonLineOrigin` takes. Where `FishingLineOrigin` keeps vanilla's value with the camera on the player, it tells `ThirdPersonLineOrigin` (a flag reset at `updateRenderState` HEAD), whose line then only moves onto a body drawn earlier in the same pass. The third-person branch isn't hooked: players other mods send down it (First Person Model, Real Camera) get the body-held rod too. It also holds the line-visibility injectors (`updateRenderState` HEAD and TAIL, and a `@WrapWithCondition` on `render`'s one `renderFishingLine` call site, which its loop reaches once per segment — `require = 0` here, unlike on the deferred versions, because that fishing-specific private method is the natural target for a mod that redraws the line and losing the condition only leaves the line visible) and the body-held line's placement at `render` (`require = 0`): a HEAD inject that works the offset out and three `@ModifyVariable`s at the STORE of `render`'s float locals 0–2 (`f`/`g`/`h`) that write it, so nothing is allocated and the state's `pos` keeps vanilla's value.
- **`FishingLineOrigin`** — replaces vanilla's guess (it doesn't reuse vanilla's eye-based vector): reads what this frame's hand pass will draw with (on 1.21.8 `HeldItemRenderer.renderItem` runs from `GameRenderer.renderHand` at the end of `renderWorld`, after the world's entities are drawn, and reads the live player and the renderer's own drawn items and equip progress, `HeldItemRendererAccessor`, at the frame's tick progress; nothing ticks in between, so the same reads during extraction match; its package-private `getHandRenderType` is mirrored), takes the rod's line attachment point from `FirstPersonRod`, applies vanilla's item sway and own view bob/hurt tilt (`GameRendererInvoker`), and places the world point, relative to the camera and with the world-only nausea/portal warp undone (its spin through `GameRendererAccessor`), on the pixel where the hand pass draws that point. Both FOVs are the ones `renderWorld` gets from vanilla's own `GameRenderer.getFov`, so zoom mods that hook it are followed: `GameRendererMixin` captures its two calls (optional `@ModifyExpressionValue`s), the world FOV before the entities are extracted (this frame's) and the hand FOV after them (last frame's, used while the world FOV's factor on top of its options-FOV-times-movement-modifier base is unchanged within float noise: that factor holds the death and fluid factors, which the hand FOV shares, and any zoom a mod multiplies in; so sprinting, speed and flying don't count; otherwise, or without the captures, `getFov` is asked through `GameRendererInvoker`: each call probes the camera's surroundings for fluid, `Camera.getSubmersionType`, a dozen world lookups and ~1 KB of garbage); 1.21.8 keeps no copy of the world projection without the bob and warp, so a mod that changes the projection itself isn't. The rod's hand comes from the drawn items; while a rod is held but none is drawn yet (a quick F-swap with a hook out) the line stays with the hand it was last drawn in. None of its inputs change within a frame (the player and the renderer's fields only in ticks, the camera once per frame), so the origin is worked out once per `HandPass` frame and reused by later extractions of the local player's hooks in it (Iris' shadow pass extracts them first, before the world's own entity pass and its hand pass; nothing it reads changes in between); a panorama capture, which renders the world without a frame of its own, is checked before that reuse. Its class Javadoc lists the steps and every case that keeps vanilla's value.
- **`FirstPersonRod`** — vanilla's first-person rod geometry. The attachment point is vanilla's screen anchor `(±0.525, -0.1)` back-projected, at the 70° hand and an assumed 16:9 calibration aspect, onto the resting rod's model mid-plane, shifted by the pack's tip delta (`RodSprite`), then carried through `swingArm` (on 1.21.8 its swing translation, then `applyEquipOffset` incl. the equip dip, then `applySwingOffset`; the two translations commute) and the `handheld_rod` display transform. 1.21.8 has no swing animations (every idle item swings the same way) and no swap-animation scale.
- **`ThirdPersonLineOrigin`** + `HeldItemFeatureRendererMixin` / `AbstractClientPlayerEntityMixin` — the line origin on a rod held by a player's body, for every line not on the first-person rod: vanilla's third-person branch for every player (MC-4490 crouch, MC-176514 riding, MC-198777 boat, MC-247425 arm swing, MC-270173 swim/crawl, MC-270174 sleep; also walking, gliding, riptide, death), and the local player whose body is drawn in first person (asleep, a mod's third-person camera, a mod drawing it such as Player Animation Library's first-person model mode). Vanilla's third-person value is a fixed offset from the eye turned by the entity's body yaw. Nothing of the pose is modelled: the rod is read where it is drawn. `HeldItemFeatureRendererMixin` (`require = 0`, priority 1500 so it runs after other mods' same-call `@Inject`s, e.g. Player Animation Library's and Animatium's item transforms) sits at `HeldItemFeatureRenderer.renderItem`'s `ItemRenderState.render` call, past its empty check, so once per non-empty held item of an armed entity: a small inlined gate (a player's hook was extracted this `HandPass` frame or the previous one, the state is a `PlayerEntityRenderState`, and its `id` together with the arm this item is drawn in is one of those hooks' owner keys: 1.21.8's `renderItem` gets no stack to tell a rod by, so these `(id, arm)` sets, filled at `updateRenderState` TAIL and by the draw-list walk below, keep other players and armour stands out) leads to the out-of-line read, which for the `getArmHoldingRod` rod of a player who is fishing (entity by `id`, `PlayerEntity.fishHook` is set on the client; the arm is re-checked against `getArmHoldingRod` **live**, since a key from the previous frame carries that frame's arm and could otherwise let the other hand's rod overwrite the right reading, and the rod itself by the live `getStackInArm`, which the item state was extracted from just before this drawing, nothing ticking in between) stores on the player (`AbstractClientPlayerEntityMixin`) the attachment point under the drawn pose, tagged with the pass (frame + the number of passes that have ended so far + either the buffer source or, for a drawing inside the world's entity loop, that loop: on 1.21.8 nothing is deferred and one `VertexConsumerProvider.Immediate`, the `GameRenderer`'s, takes every vanilla pass of a frame — the world's entities and block entities, the first-person hand, the screen effects, and the GUI's pictures such as the inventory's player model. Two optional hooks end a pass: `WorldRendererMixin` marks `WorldRenderer.renderEntities`' return (priority 1500, so a body other mods draw there — Freecam's Show Player, Real Camera's classic mode — is still part of the entity pass; nothing marks its head, so First Person Model's body, drawn there, belongs to the pass that follows), and `VertexConsumerProviderImmediateMixin` counts `VertexConsumerProvider.Immediate.draw()`. The first keeps the GUI's pictures apart from the world's entities even when a mod replaces the buffer sources so vanilla's `draw()` never runs (ImmediatelyFast's `BatchableBufferSource` overrides it without calling super); the second separates passes that share one entity loop. Nothing inside `renderEntities` flushes, so a rod and a hook of the same entity loop stay in one pass; with neither hook applied no pass is ever matched, and every body-held line keeps vanilla's value. The collector alone would not do, because a mod may hand each entity its own — **Iris with a shader pack** does: its `entity_render_context/MixinEntityRenderDispatcher` `@ModifyVariable`s the buffer-source argument of every `EntityRenderDispatcher.render` into a freshly allocated `BufferSourceWrapper` as soon as a pack has set `WorldRenderingSettings.entityIds`, which nothing resets, so it outlives unloading the pack until the game restarts, and a rod and its hook never share one. What they do share is the loop: `WorldRendererMixin`'s head inject records the pass this entity loop opens in (frame + pass-end count) before the first entity, every drawing notes whether it happened while that record still held, and the match takes two such drawings of one loop as the same pass however their collectors differ. The pose is the loop's own `MatrixStack` either way, which is what the collector was ever a proxy for. Iris' shadow pass never goes through `renderEntities` and is drawn before the head records anything, so its drawings see the previous frame's record and note themselves as outside (it keeps pairing by collector, as before: its own one buffer source without a pack, per-entity wrappers with one); the GUI's pictures are past the loop's end mark and past every buffer-source flush, so their pass-end count differs; and without the optional head inject nothing is ever inside a loop and the match is the collector's alone, exactly as before. A body drawn inside `renderEntities` but into another collector is now matched where it used to fall back to the remembered spot — a glowing player or a spectator's outlines (`OutlineVertexConsumerProvider`), and a mod's own buffer source used inside that loop). 1.21.8 extracts and draws each entity in turn (`EntityRenderDispatcher.render`), so an owner drawn before its hook isn't known from this frame yet — hence the previous frame's owner set, and hence every player's hook counting for it, not only a body-held one; a hook whose owner is drawn before it would have no reading in the hook's very first frame — which is why the bobbers-last walk stamps the gate with the owners it finds in the draw list, so a hook of the world's pass is read in the frame it appears, as on 1.21.9+ and 26.x. A hook outside that list — Iris' shadow pass, or a body another mod draws at `renderEntities`' own head, before the walk gets there — still falls back for its first frame, to the last drawing of that rod or, failing that, vanilla's value. **Which of the two comes first would otherwise be a coin toss on 1.21.6–1.21.8**: `WorldRenderer` sorts the entities it is about to draw by `entity.getType().hashCode()` (`ENTITY_COMPARATOR`, added in 1.21.6, gone again in 1.21.9) and `EntityType` inherits `Object.hashCode`, so whether the player group or the fishing-bobber group is drawn first would be an identity hash — arbitrary, and different in every launch. A second optional inject, at `renderEntities`' head (`ThirdPersonLineOrigin.sortBobbersLast`), settles it: the fishing bobbers are moved behind every other entity, both parts keeping their order, so the bodies are drawn first and every body-held line sits on the rod of this very frame. It is an in-place stable partition of the list vanilla is about to iterate — invisible to the rest of `WorldRenderer`, whose only other uses of it are the F3 entity count (taken before the sort) and the `clear()` later in the same frame — and not a wrapper around `ENTITY_COMPARATOR`, whose `List.sort` call sits in an unnamed lambda of the frame graph's main pass: hooking the list at the last named method before the loop needs no synthetic name and runs after any sort, vanilla's or a mod's. The same walk stamps the rod-reading gate with the owners of the bobbers it passes, which is what makes the first frame of a cast exact on this family: from 1.21.9 on, and on 26.x, vanilla extracts every entity before submitting any, so a hook's extraction always precedes its owner's rod and those branches gate on this frame alone — here the two are interleaved, and the draw list is that same knowledge one step early (every bobber in it is extracted a moment later in the loop this precedes). That is why the walk is unconditional and not itself gated: a gate would skip the one frame it is needed for. With no bobber in the list it is a type check per drawn entity and nothing else — no write, no allocation; each bobber then adds the `Optional` that `LazyEntityReference.resolve` makes inside `getPlayerOwner`, of which there are only ever a handful. Next to it, one statement earlier, sits `renderedEntities.sort(ENTITY_COMPARATOR)` over the same list — an O(n log n) sort that boxes two `Integer`s per comparison. Reordering is as close to free of consequence as the renderer allows: `entity_cutout` on the bobber's texture is opaque and depth-writing and `line_strip` blends but writes depth and carries alpha 255, neither is a `translucent` layer (so neither is quad-sorted at draw time), no translucent layer moves relative to another, a glowing bobber's outline copy carries the colour set for that entity right before it draws (`entity_cutout` does affect the outline, `line_strip` doesn't), and neither bobber layer has a dedicated allocator in `BufferBuilderStorage`, so a bobber costs its two draw calls wherever it sits and moving one contiguous run is worth at most one draw call at the seams, only ever one fewer. What is left is the one pairing a reorder can decide: a bobber behind an entity layer that blends and writes depth, which `entity_translucent` does and every player body uses (`PlayerEntityModel`), so it is now always drawn after that body and depth-rejected where it used to be a coin toss. The layer's 0.1 alpha cutout and skins being alpha 0 or 255 make that a non-event — a pixel that would hide the bobber hides it either way, one that wouldn't is discarded before it writes depth — and vanilla's identity-hash order already decided it differently in every launch. The inject sits after vanilla's sort, so replacing or cancelling `ENTITY_COMPARATOR` changes nothing; what takes it out is a mod that keeps the mixin from applying, draws the entities without going through `renderEntities`, or re-orders the list from a head inject that applies after this one (Mixin resolves every injector's target instruction before any of them inserts anything, so at a head, as at a return, a later application — a higher mixin priority, or an `@Inject(order = )` above the default 1000, which is sorted before priority — runs later; hence 1500 here too). Then the coin toss is back and both orders still work: hooks first means every one of them takes the remembered spot (one frame late), while the rod drawn later in the same pass refreshes that spot at the hook's own world position. The owner, its partial tick and the same-pass-only flag ride on the hook's render state (set at `updateRenderState` TAIL, dropped at its `render`: on 1.21.8 one `EntityRenderer` keeps one render state for every entity of its type, for the client's whole life, so the last hook of a world would otherwise keep its owner — and its world — alive until the next hook is extracted; other mods keep render states past their frame too, as Iris' shadow pass keeps its last frame's, also after a disconnect); the pending offset is cleared once `h` is written and the last hook's pass (its buffer source) at the next frame's start (`GameRendererMixin`), so no static reference outlives its drawing or frame. At the hook's `render` HEAD, when the owner's rod was drawn earlier in the same pass, the line offset is that point through the inverse of the hook's pose (a pass that turns its root cancels out), minus the line's 0.25 lift. Otherwise it is the tip where the rod was last drawn, relative to the body's position and turned with its yaw (`LivingEntityRenderer.clampBodyYaw` mirrored), while the owner still holds a rod in that arm; a pose or mount change invalidates that offset, and it is kept anyway, because a one-frame lag is far less visible than a one-frame teleport — not because it is the closer of the two candidates. Usually it isn't: measured against the tip as drawn on the transition frame, vanilla's value is nearer for most of them (leaving gliding or a riptide spin 2.15 blocks or more for the kept reading against 0.12, waking 0.8–2.1 against 0.12, a crouch 0.54 against 0.07), and the kept reading only wins leaving swimming (1.04 against 2.12) and lying down (0.81 against 1.39); a mount change or a lean that ramps up is small either way. What the leniency buys is the frame the origin would otherwise jump to a different anchor and back, which is the visible artifact; with the order forced this whole path is a fallback rather than the usual one. The yaw re-rotation follows the pose the reading was taken in, which is the convention the offset is in. The remembered offset carries the render offset of the frame it was read in (`EntityRenderer.getPositionOffset(S)`, which the pose includes and the body position it is measured against does not): it cancels while that offset holds, and a player's is the crouch shift, which the remembered path's pose gate keeps in step, plus the experimental minecart's lerp, which it does not — a frame of that lerp out on the fallback path, and still far nearer the rod than vanilla's guess. Re-deriving it would mean re-deriving a vanilla method any mod may override, at the reading and at the replay. An older reading isn't kept; else vanilla's value. A first-person line `FishingLineOrigin` left at vanilla's value (see its Javadoc) with the camera on the player takes only the same-pass rod, never the remembered one: no body is on screen, and the remembered spot (from an F5 view just left, or from Iris' shadow pass, whose entity collection doesn't skip the camera entity as `WorldRenderer`'s does and so draws the local body with its rod, then the hook) would start the visible line at a rod that isn't drawn. Iris' shadow pass carries no line of its own: it exists only with a shader pack, and with one every entity render gets its own buffer source, so its rod and its hook never pair — nor does it call `renderEntities` (it sorts its own list by the same identity hash), so neither the sort hook nor the loop tie reaches it. Player Animation Library's first-person body (drawn earlier in the world pass) still carries the line. With the camera on another entity vanilla never draws the local player, so a drawn body is a mod's and may come after the hooks (Freecam's Show Player draws it itself at `WorldRenderer.renderEntities`' TAIL, after every other entity): that line keeps the remembered spot, as Real Camera's classic mode does. The remembered offset is taken whenever a hook of the pass gives the world position (also for a rod drawn after its hook, as Real Camera's classic mode does). Exceptions disable it until the next world; without frame counting nothing is read.
- **`ThirdPersonRod`** — the body-held rod's attachment point in the space `HeldItemFeatureRenderer` submits the item in: the rod's tip (`RodSprite`; not first person's vanilla anchor, which sits by the tip only at first-person scale and angle) on the model mid-plane, through the `handheld_rod` `thirdperson_righthand` display transform (the left hand's is the same after `Transformation.apply`'s left-hand fix). Cached per frame.
- **`RodSprite`** — the tip of the `item/fishing_rod_cast` sprite, the rod model's source in every view (on 1.21.8 in the block atlas, which holds the item textures: `JsonUnbakedModel` resolves an item model's textures against `SpriteAtlasTexture.BLOCK_ATLAS_TEXTURE`, which is deprecated but is still the key `BakedModelManager.getAtlas` takes): a resource pack's redrawn sprite is measured (visible pixels at/above the item alpha cutout, unioned over animation frames; a shift beyond `MAX_TIP_SHIFT`, the measurement's one tuned constant, is ignored as a misread; the scan only covers the sprite's top-right corner, where a usable tip can be, and a sheet too large to measure inside a frame's budget keeps vanilla's tip), cached per `SpriteContents` identity, i.e. per resource reload. 1.21.8 has no `SpriteContents.isAnimated()`, so its private `getFrameCount()` stands in (`SpriteContentsAccessor`): it is `> 1` exactly when the sprite has an animation, and only then are the `getDistinctFrameCount()` tiles read instead of tile 0. The tile grid is not a substitute — an `.mcmeta` sizes the sprite even when its frame list collapses to a null animation, so a multi-tile image can be unanimated.
- **`FishingLineVisibility`** + `FishingBobberEntityStateMixin` / `FishingBobberEntityMixin` — hides the line (not the bobber) of a hook whose rod has left its owner's hands, in every perspective and for every player (MC-310980, MC-211561): the server removes such a hook only a tick plus the ping later, or never while the tick rate is frozen. Where `FishingLineOrigin` placed the line on the drawn first-person rod, it stays until the lowering rod is gone from the drawn items (a first-person line left at vanilla's value hides at once: vanilla would start it at the off-hand side, where no rod is). Only hooks whose owner was seen holding a rod (a flag on the hook) are hidden, so hooks cast by other items keep vanilla's line; for the local player a rod among the drawn items counts too (the own hook arrives a round trip after the cast). Decided at the end of `updateRenderState`, carried on the render state, applied by a `@WrapWithCondition` (MixinExtras v2) on `render`'s one `renderFishingLine` call site, which its loop reaches once per segment; an exception leaves lines visible until the next world or dimension.
- **`HandPass`** + `GameRendererMixin` / `HeldItemRendererMixin` — whether the hand pass reached a hand last frame (frames counted where `GameRenderer.render` calls `GlobalSettings.set`, i.e. once per rendered frame: the first call in its `!skipGameRender` block, through which Dynamic FPS skips most frames while throttling (a skipped frame counted as one without a hand would put the line at vanilla's value), the frame marked where the five-argument `HeldItemRenderer.renderItem` calls `renderFirstPersonItem`, past any cancel; also reached while scoping, where nothing is drawn, so `FishingLineOrigin` checks scoping itself). No rod on screen → vanilla's value, whatever hid the hand (spectator, a mod cancelling the hand pass), unless the player's own body is drawn with the rod in the world pass (asleep, a third-person camera; Player Animation Library's first-person model mode, whose body counts only when drawn earlier in the same pass than the hook): then `ThirdPersonLineOrigin` puts the line on that rod. The HUD hidden with F1 is the exception: it hides the hand but not the line, a world object, so the line stays corrected where the rod would be. The frame counter runs before the camera update, which 1.21.8 does inside `renderWorld` (no separate `updateCamera`), so right after `renderWorld`'s `Camera.update` call (after the tick, before the entities and the hand pass) `HandPass` samples the live `GameOptions.hudHidden` (which `renderHand` reads later in the frame) and the rest of `renderHand`'s gate (first person, not rendering a panorama, awake, not spectating), plus the camera on the player, not in third person and at the player's eye where `Camera.update` puts it (some freecam mods keep the player as camera entity and don't move the camera into third person; the smoothed eye height comes through `CameraAccessor`). At the next frame's start it latches whether a hand is drawn when only the HUD decides, from frames that prove it (a drawn hand; a missing one with the HUD and the gate open means a mod hid it); a frame with the gate closed, or one that didn't render the world, restores the default (drawn). While the HUD is hidden (this or the previous frame) the line stays corrected if that latch holds and the gate is open this frame. So a hidden HUD never moves the line (Camerapture's photo frame and freecams on their own camera entity keep vanilla's value, unless they draw the player's body, as Freecam's Show Player, its default, does: then the body's rod, one frame late, from the remembered spot; freecams that move the player's camera into third person keep the body's rod; F5, sleep or spectator before F1 don't stick). Mods that keep the hand while hiding the HUD (Better F1) stay corrected through the normal path. These injects are `require = 0`: if the counter or the mark is blocked, the line just stays vanilla, and `FishingLineOrigin` logs one warning (frame counter never ran, or no hand mark seen while fishing in first person); without the sampling, F1 leaves vanilla's line.
- **`SpriteContentsAccessor`** — `@Accessor` for `SpriteContents.image` and `@Invoker` for its private `getFrameCount()`, which stands in for the `isAnimated()` 1.21.8 doesn't have. **`CameraAccessor`** — `@Accessor`s for `Camera.cameraY`/`lastCameraY`. **`GameRendererInvoker`** — `@Invoker`s for `GameRenderer.tiltViewWhenHurt`/`bobView`/`getFov`. **`GameRendererAccessor`** — `@Accessor`s for `GameRenderer.nauseaEffectTime`/`nauseaEffectSpeed` (the warp's spin) and `fovMultiplier`/`lastFovMultiplier` (the movement FOV modifier, for the shared FOV factor). **`HeldItemRendererAccessor`** — `@Accessor`s for `HeldItemRenderer`'s drawn items and equip progress. **`VertexConsumerProviderImmediateMixin`** — counts `VertexConsumerProvider.Immediate.draw()` calls for `ThirdPersonLineOrigin`'s pass tag (`@ModifyExpressionValue`, `require = 0`, on the method's only field read, so nothing is allocated). **`WorldRendererMixin`** — two optional `@Inject`s on `WorldRenderer.renderEntities` (`require = 0`, mixin priority 1500 so both run after other mods' default-order injects at the same point, at the head as at the return): at TAIL it marks the pass's return for the same tag (a body other mods draw there is still inside the pass; the head is deliberately not marked as a pass end, so a body drawn there belongs to the pass that follows), which is what still separates the world's entities from the GUI's pictures when a mod replaces the buffer sources; at HEAD it moves the fishing bobbers to the back of the list vanilla is about to draw, so a fishing player's body precedes the hooks it cast. **`FishingRodFix`** — the shared logger, `isRod` and `holdsRod`.

Declared incompatible: Enchanted Fishing Line (`enchanted_fishing_line`, all versions) is listed under `breaks` in `fabric.mod.json`, so the loader refuses to start with both and shows its incompatible-mods screen. Its builds (1.0.0 for 26.2 and 26.1–26.1.2, 1.0.0-hotfix for 1.21.11) carry a copy of this mod's v0.5 correction as a cancellable `@Inject(RETURN)` on the hand-position method (`getHandPos` here) with no check for this mod. v0.5's own RETURN inject cancelled first, so only one correction applied; v0.6's first-person hook sits inside the method and can't pre-empt it, so EFL's copy stacked on the corrected origin (off the rod on windows other than 16:9, with FOV modifiers, while turning and crouching), and its rope, drawn by its own call from the state's line origin, got neither the body-held offset nor the line hiding. User decision 2026-09-22: `breaks` on every branch, no EFL-specific code.

Known limitations: per-item model swaps (server `custom_model_data`/`item_model`, CIT), 3D rod models and changed display transforms are not measured; mods that re-pose the hand in the renderer without touching the state it reads (viewmodel mods such as Punchy, ViewModel, ScaleMe, Smallhands, Animatium's legacy item positions and 1.7 fishing rod (both on by default; its own 1.7/1.8 shift of vanilla's line the correction replaces), Mine Little Pony's first-person unicorn magic, CameraTweaks' first-person freelook, Inspect Animations), shaderpack hand sway, portal-view mods that move the camera (Immersive Portals), Polytone line offsets and Tide's own hook renderer are not covered (neither has a 1.21.6–1.21.8 build today; kept here for when one appears); on 1.21.8 the hand pass reads the live player and its renderer's fields, and its hand selection (`HeldItemRenderer.getHandRenderType`) is mirrored, not read, so a mod that changes `renderItem`'s locals or arguments (swing, sway, equip dip, the drawn item: Animatium's "Fix Equip Animation Item Check", on by default, hands the main-hand call its own copy of the selected stack) or that selection isn't followed (a hand it hides keeps the line at the hidden rod; one it draws where vanilla wouldn't keeps vanilla's value), while mods that change the renderer's fields (Animatium's equip changes in `updateHeldItems`) are; the world FOV is `getFov`'s, so mods that change the world projection itself rather than `getFov` (an orthographic camera, a lens) aren't followed, nor, reliably, Zoomify's "Affect Hand FOV" turned off (not its default), which zooms the hand back at `renderWorld`'s call (`getFov` ordinal 1) rather than inside `getFov`: both are `@ModifyExpressionValue`s on that instruction and mixin priority 900 against Zoomify's default 1000 now makes this mod's capture the outermost, so with a steady zoom it reads Zoomify's final value and the line is on the rod. It is still off during zoom changes (the shared-factor test fails and the `getFov` fallback carries Zoomify's `@ModifyReturnValue` zoom, which its call-site modifier would have undone) and with an Iris shader pack (Iris' `HandRenderer` calls `getFov` itself, bypassing that call site), as vanilla's is; Tweakeroo's free camera makes both FOVs the options FOV (it forces `changingFov` false and replaces `getFov`'s 70), so the line is off the rod while it is on; mods that bob or sway the hand and world passes differently (BetterHandBobbing, View Bobbing Options, No Screen Bobbing, Tweakeroo's world view-bob toggle, Animatium's Minimal View Bobbing, ShakeTweaks' bob toggles and "Disable Hand View Sway"), and Clearviews with "Disable Nausea" turned off, leave the same mismatch vanilla has; mods that drop the nausea warp without Clearviews' mod id (anti-nausea in Meteor, Wurst, LiquidBounce) make the line swing around the rod under nausea/portal — Clearviews and Iris shaders don't collide here: Iris redirects other instructions (`Double.floatValue()` and `Matrix4f.rotation(Quaternionfc)`) and, with a pack on, zeroes the warp intensity, so Clearviews' own wrappers never run; mods that hide one arm by cancelling its `renderFirstPersonItem` (Hide Hands, Tweakeroo's Disable Offhand Rendering; Exposure has no 1.21.6–1.21.8 build), or only its item (Player Animation Library during a first-person transition), leave the line at the hidden rod's tip, as do mods that hide the hand only after F1 was pressed (Camerapture's camera, Snapmatica's viewfinder, Picture Mode); conversely a mod that stops hiding the hand while F1 is on (Snapmatica's viewfinder or a freecam parked at the eye) leaves vanilla's line until F1 is released; camera-smoothing mods (SmoothCamera) drop the F1 line to vanilla's value during their F5/teleport glide; a local cast followed by a slot switch before the hook reaches the client, on a ping longer than the drawn items' few-tick lag, keeps vanilla's line until the server removes the hook. On a player's body (third person): the rod is read where `HeldItemFeatureRenderer` submits it, so everything that poses the body, arm or item before that call is followed (animation mods, held-item position mods, First Person Model's offset body, Mine Little Pony's ponies), but not what changes the item after it (a resource pack's changed `thirdperson` display transform, per-item or 3D rod models, Animatium's 1.7 stick rod, a wrap, redirect or argument change of that call, or a same-call `@Inject` above priority 1500; Animatium can also cancel a sleeping player's body render and force the cast rod model on or off, so the drawn sprite may not be `item/fishing_rod_cast`), nor rods drawn outside the pass the hook's line is drawn in (Real Camera's default binding mode, Mine Little Pony's magic ponies with third-person magic and a player with the glowing effect or a spectator's outlines are all inside that pass now and matched, since each is a drawing of the same entity loop, whatever collector it goes into; see below) or not through that feature renderer (morph mods such as Woodwalkers: vanilla's value). Mine Little Pony's magic now starts the line at the glow copy's tip rather than at vanilla's value: its `HeldItemFeature` draws the item three times for one arm — the real one, then two glow copies through its own wrapped vertex-consumer provider — all three inside the entity loop with the same `MatrixStack`, and the reading is last-write-wins, so the glow copy is what gets stored and the loop tie matches it (a fraction of a block from the real levitating rod, and far closer than vanilla's guess; Mine Little Pony 4.14.4+1.21.7, checked 2026-09-23). Real Camera's binding mode, its default, draws the body into its own `MultiVertexCatcher` at `renderEntities`' return, at the default injector priority and so inside the entity loop: the loop tie matches it too (the catcher re-emits the caught positions into the pass's own buffer source, in the pass's space), so its line starts where the body's rod was drawn, one frame late as for any rod drawn after its hook, instead of keeping vanilla's value; classic mode already matched by collector (Real Camera 0.7.4-beta-1.21.8, checked 2026-09-23). Likewise Freecam with Show Player off (its own camera entity, the body hidden) starts the line where the hidden body's rod was last drawn while the pose matches: after an F5 view, and — on the versions where its Iris mixin cancels a method Iris never calls, so the shadow pass still draws the hidden body and rod — every frame with Iris entity shadows (checked on Freecam 1.3.5; 1.21.6–1.21.8's build is 1.3.4+mc1.21.6, where only its `renderEntities` TAIL body draw was re-read). Where the owner's rod isn't drawn in the pass before its hook (the owner out of view, a hook that arrived before its owner, a body drawn after the hooks), the line starts where it was last drawn, turned with the body (except a reading taken asleep, which is in the bed's space: vanilla turns a sleeping body by the bed's direction, not by the body yaw, so that reading is used unturned); a changed arm pose (a swing) shows when the rod is drawn again, a pose or mount change is followed only as far as a reading from the previous frame allows (one frame of pose change, then the next drawing settles it), and a player never seen with the rod drawn, or in another pose for more than a frame, keeps vanilla's value until it is drawn again (a jump then); a player who starts drawing another way in the same pose while fishing (a morph mid-cast) keeps that remembered spot. A rod hidden by another mod (Not Enough Animations' off-hand hiding) leaves the line where the rod was last drawn; hidden in bed (its default) the line keeps vanilla's value unless the rod was seen drawn in bed before. The state's `pos` keeps vanilla's value for a body-held rod, so a mod that reads it sees that. A body drawn at `renderEntities`' own head, before the pass is recorded, is outside the window — First Person Model injects there at the default priority, below the port's — so with an Iris shader pack, where the collector no longer ties anything, its body is the one inside the loop the fix does not reach (without a pack the shared buffer source still matches it). A mod rendering the world twice per frame into one buffer source without flushing it in between could hand one pass's rod to the other (vanilla's passes each end with a `draw()`, which ends a pass here). A hook whose owner is drawn before it has no rod reading in its very first frame (the gate at the held-item call runs on the hooks of the frame before), so that one frame keeps vanilla's value or the remembered spot. The bobbers-last inject (see the Architecture section) is what keeps the body-held line on this frame's rod on 1.21.6–1.21.8, where vanilla's entity order is an identity hash and would otherwise draw every hook before every body in about half of all launches, for the whole session. A mod that keeps that mixin from applying, draws the entities without going through `renderEntities`, or re-orders the list from a head inject of a still higher mixin priority brings the coin toss back (replacing or cancelling vanilla's own sort does not — the inject runs after it): on the losing side the body-held line is one frame late (visible on a fast arm swing; a pose or mount change keeps the previous frame's reading rather than falling back to vanilla, so the origin never jumps to a different anchor for a frame — the lag is largest leaving swimming, gliding or a riptide spin and when lying down or waking), and a line `FishingLineOrigin` left at vanilla's value with the camera on the player (Player Animation Library's first-person body) keeps it, since that case takes only a rod drawn earlier in the same pass. The inject only orders the entities `WorldRenderer` itself draws, so a pass that collects them another way (Iris' shadow pass) keeps whatever order it has.

## Dev environment gotcha

Loom writes `.idea/runConfigurations/Minecraft_Client.xml` only when it is missing and never updates it, and `.idea` is shared by every branch of the checkout. A stale config on the 26.3 branch lacks `-XX:StackShadowPages=32` (from Mojang's version JSON), and the client then dies natively on an in-world resource reload (access violation in `jvm.dll`, no `hs_err`). A 26.x config on an old branch fails to start on JDK 21 (`--sun-misc-unsafe-memory-access`). After switching version families, delete the XML and run `./gradlew ideaSyncTask`.

## Versioning

Each Minecraft version lives on its own branch (e.g. `1.21.4`, `1.21.11`, `26.3`). The version numbers in `gradle.properties` (`minecraft_version`, `loader_version`, `loom_version` — on branches not yet ported to the current fix the Loom version sits in `build.gradle`'s `plugins` block instead — and `yarn_mappings` on pre-26 branches) must be updated together when porting to a new MC version. The `mod_version` in `gradle.properties` is independent of MC version.

## Roles

Project roles:

- `/port-version <mc_version>` — ports the mod (the current reference fix from the default branch) to a target Minecraft version, backport or forward-port. It reviews the port in rounds with `/reviewer` (correctness and performance per round, compatibility once in parallel) until no real bug is left, fixes the rest, and only then launches the game. See `.claude/skills/port-version/SKILL.md`.
- `/reviewer [scope] [--only <dimensions>] [notes]` — read-only, one-pass review of the branch's unpublished changes (or a range, paths, or `all`). Fresh reviewer agents check the default review, a performance gate (the mod's cost within noise of zero on a whole frame's budget) and compatibility with known mods, shader packs and resource packs; the findings are verified and returned as one report. It never edits, builds or commits. See `.claude/skills/reviewer/SKILL.md`.
