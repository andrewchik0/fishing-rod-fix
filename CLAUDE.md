# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A client-side Fabric mod for Minecraft that fixes vanilla bugs where the fishing line starts in the wrong place. In first person the line origin is placed on the rod the hand pass actually draws, at vanilla's own attachment point by the tip: across aspect ratios, world and hand FOV, the rod's equip dip, swing and sway, view bob, hurt tilt and nausea warp, the camera's smoothed eye height, and resource packs that redraw the rod. On a player's body (third person, other players, sleeping in any view) it is placed on the tip of the rod the body is drawn holding, in whatever pose the model is in.

Each Minecraft version lives on its own branch and the code differs per version family (see Versioning). This branch targets **MC 1.21.4** (obfuscated: yarn mappings, remapped by Loom; the jar declares `>=1.21.4 <=1.21.4` and is named `fishingrodfix-1.21.4-v<mod_version>.jar`). 1.21.4 draws the line and the held items directly — the deferred render-command queue arrived in 1.21.9 — so the line is a `renderFishingLine` loop in `FishingBobberEntityRenderer.render`, held items go through `HeldItemFeatureRenderer.renderItem`, and every pass of a frame draws into the `GameRenderer`'s one `VertexConsumerProvider.Immediate`. Entity render states already exist (they arrived in 1.21.2), but `WorldRenderer.renderEntities` extracts **and** draws each entity in turn, and it draws them in the order the client added them (`ClientWorld.getEntities()`, an `Int2ObjectLinkedOpenHashMap` in `EntityIndex`): there is no `ENTITY_COMPARATOR` — that entity-type-identity-hash sort existed only from 1.21.6 to 1.21.8. So vanilla's own order already draws a body before the hooks it cast, and the branch forces it anyway, because Iris regroups that list by entity type whenever it is installed (see the Architecture section). 1.21.11's spears (`ItemStack.getSwingAnimation`, swap-animation scales) and the items atlas (1.21.11) don't exist here; `SpriteContents.isAnimated()` doesn't either.

Compared with the `1.21.5` branch (the port's reference), everything the fix mixes into or reads is the same code under different yarn names, with **one** behavioural exception: the nausea/portal warp. 1.21.4's `GameRenderer.renderWorld` spins it by `(ticks + tickDelta) × (the nausea effect held ? 7 : 20)` degrees from a private `int ticks` counter, and takes its intensity straight from `ClientPlayerEntity.nauseaIntensity` (which `tickNausea` feeds from the portal *and* the effect), where 1.21.5 replaced the counter with a `nauseaEffectTime`/`nauseaEffectSpeed` pair and maxes the intensity with `getEffectFadeFactor(NAUSEA)`; `GameRendererAccessor` exposes `ticks` here instead. The renames are `Camera.getLastTickDelta`, `RenderTickCounter.getTickDelta`, `Entity.prevX/prevY/prevZ`, `LivingEntity.prevBodyYaw`/`prevHeadYaw`, `HeldItemRenderer.prevEquipProgress*` and `ClientPlayerEntity.prevNauseaIntensity` (1.21.5: `getLastTickProgress`, `getTickProgress`, `lastX/Y/Z`, `lastBodyYaw`/`lastHeadYaw`, `lastEquipProgress*`, `lastNauseaIntensity`). Every injection target, descriptor and bytecode ordinal is unchanged: `getHandPos(PlayerEntity, F, F)Vec3d` with its one `Vec3d.add(Vec3d)` (third-person branch first in the bytecode, as everywhere), `render(FishingBobberEntityState, MatrixStack, VertexConsumerProvider, I)` with `f`/`g`/`h` as float ordinals 0–2 in LVT slots 7–9 and one `renderFishingLine` call, `updateRenderState`'s own return in the owner-less branch (so Mixin's `TAIL`, the last return, never fires for one), `renderWorld`'s single `GameRenderer.getFov` INVOKE and its `Camera.update(BlockView, Entity, ZZF)`, `renderHand(Camera, F, Matrix4f)`'s single `getFov`, `render`'s single `MinecraftClient.isFinishedLoading()` inside its `!skipGameRender` block, the five-argument `renderItem`'s two `renderFirstPersonItem` calls, `HeldItemFeatureRenderer.renderItem`'s single `ItemRenderState.render` and `VertexConsumerProvider.Immediate.draw()`'s single `layerBuffers` read. `handheld_rod.json` and `fishing_rod_cast.png` are byte-identical to 1.21.5's, so the measured vanilla rod tip is the same `(15, 1)/16`.

**1.21.4 is its own jar** (checked 2026-09-23): it cannot reach down to 1.21.2–1.21.3. 1.21.4's item-model rework introduced `ItemRenderState`, `ItemModelManager` and `ArmedEntityRenderState`, none of which exist in 1.21.3 or 1.21.2 (which still carry `ModelOverrideList`), so `HeldItemFeatureRendererMixin`'s injection target and `ThirdPersonLineOrigin`'s render-state type would not resolve at all — and the intermediary client-only jar changes 641 classes, drops 901 and adds 1775 between 1.21.3 and 1.21.4. Upwards, 1.21.5 renames the fields above and reworks the warp. The upper bound is closed (`<=1.21.4`) rather than `<1.21.5`: Fabric normalises a snapshot or pre-release into a semver pre-release of the *next* release (`1.21.5-alpha.…`), which sorts below `1.21.5` and would satisfy `<1.21.5`.

## Build Commands

```bash
# Build the mod (produces JARs in build/libs/)
./gradlew build

# Run the Minecraft client with the mod loaded
./gradlew runClient

# Generate sources and set up IDE
./gradlew genSources
```

CI builds with Java 21 (`release 21`); `gradle/gradle-daemon-jvm.properties` makes Gradle run on a JDK 21 for this branch (Loom 1.18+ would need Gradle on JDK 25, so the branch stays on Loom 1.17).

## Architecture (1.21.4)

Purely client-side; no access widener and no Fabric API dependency (MixinExtras ships with Fabric Loader). Loom remaps the mixins' targets to intermediary itself (no refmap).

- **`FishingBobberEntityRendererMixin`** (`src/client/java/.../mixin/client/`) — `@ModifyExpressionValue` (`allow = 1`) on the only `Vec3d.add(Vec3d)` in `FishingBobberEntityRenderer.getHandPos`, i.e. the result of vanilla's first-person branch: delegates to `FishingLineOrigin`, or keeps vanilla's value while vanilla draws the player's own body (asleep, or a third-person camera on the player in first person), whose rod `ThirdPersonLineOrigin` takes. Where `FishingLineOrigin` keeps vanilla's value with the camera on the player, it tells `ThirdPersonLineOrigin` (a flag reset at `updateRenderState` HEAD), whose line then only moves onto a body drawn earlier in the same pass. The third-person branch isn't hooked: players other mods send down it (First Person Model; Real Camera on the versions it has a build for) get the body-held rod too. It also holds the line-visibility injectors (`updateRenderState` HEAD and TAIL, and a `@WrapWithCondition` on `render`'s one `renderFishingLine` call site, which its loop reaches once per segment — `require = 0` here, unlike on the deferred versions, because that fishing-specific private method is the natural target for a mod that redraws the line and losing the condition only leaves the line visible) and the body-held line's placement at `render` (`require = 0`): a HEAD inject that works the offset out and three `@ModifyVariable`s at the STORE of `render`'s float locals 0–2 (`f`/`g`/`h`, LVT slots 7–9, the method's only float stores) that write it, so nothing is allocated and the state's `pos` keeps vanilla's value. `updateRenderState` returns early for a hook without a player owner (after zeroing the state's `pos`), and Mixin's `TAIL` is the method's *last* return, so the TAIL never runs for one and the HEAD's reset is what leaves it at vanilla's behaviour; the helpers still take a null owner as cheap defence against a mod that nulls the local.
- **`FishingLineOrigin`** — replaces vanilla's guess (it doesn't reuse vanilla's eye-based vector): reads what this frame's hand pass will draw with (on 1.21.4 `HeldItemRenderer.renderItem` runs from `GameRenderer.renderHand` at the end of `renderWorld`, after the world's entities are drawn, and reads the live player and the renderer's own drawn items and equip progress, `HeldItemRendererAccessor`, at the frame's tick progress; nothing ticks in between, so the same reads during extraction match; its package-private `getHandRenderType` is mirrored), takes the rod's line attachment point from `FirstPersonRod`, applies vanilla's item sway and own view bob/hurt tilt (`GameRendererInvoker`), and places the world point, relative to the camera and with the world-only nausea/portal warp undone (its spin through `GameRendererAccessor`), on the pixel where the hand pass draws that point. Both FOVs are the ones vanilla's own `GameRenderer.getFov` returns for this frame, so zoom mods that hook it are followed: `GameRendererMixin` captures each (optional `@ModifyExpressionValue`s), the world FOV at `renderWorld`'s only `getFov` call, before the entities are extracted (this frame's), and the hand FOV at `renderHand`'s only one, which runs at the end of `renderWorld` after them (so last frame's, used while the world FOV's factor on top of its options-FOV-times-movement-modifier base is unchanged within float noise: that factor holds the death and fluid factors, which the hand FOV shares, and any zoom a mod multiplies in; so sprinting, speed and flying don't count; otherwise, or without the captures, `getFov` is asked through `GameRendererInvoker`: each call probes the camera's surroundings for fluid, `Camera.getSubmersionType`, a dozen world lookups and ~1 KB of garbage); 1.21.4 keeps no copy of the world projection without the bob and warp, so a mod that changes the projection itself isn't. The rod's hand comes from the drawn items; while a rod is held but none is drawn yet (a quick F-swap with a hook out) the line stays with the hand it was last drawn in. None of its inputs change within a frame (the player and the renderer's fields only in ticks, the camera once per frame), so the origin is worked out once per `HandPass` frame and reused by later extractions of the local player's hooks in it (Iris' shadow pass extracts them first, before the world's own entity pass and its hand pass; nothing it reads changes in between); a panorama capture, which renders the world without a frame of its own, is checked before that reuse. Its class Javadoc lists the steps and every case that keeps vanilla's value.
- **`FirstPersonRod`** — vanilla's first-person rod geometry. The attachment point is vanilla's screen anchor `(±0.525, -0.1)` back-projected, at the 70° hand and an assumed 16:9 calibration aspect, onto the resting rod's model mid-plane, shifted by the pack's tip delta (`RodSprite`), then carried through `swingArm` (on 1.21.4 its swing translation, then `applyEquipOffset` incl. the equip dip, then `applySwingOffset`; the two translations commute) and the `handheld_rod` display transform. 1.21.4 has no swing animations (every idle item swings the same way) and no swap-animation scale.
- **`ThirdPersonLineOrigin`** + `HeldItemFeatureRendererMixin` / `AbstractClientPlayerEntityMixin` — the line origin on a rod held by a player's body, for every line not on the first-person rod: vanilla's third-person branch for every player (MC-4490 crouch, MC-176514 riding, MC-198777 boat, MC-247425 arm swing, MC-270173 swim/crawl, MC-270174 sleep; also walking, gliding, riptide, death), and the local player whose body is drawn in first person (asleep, a mod's third-person camera, a mod drawing it such as Player Animation Library's first-person model mode). Vanilla's third-person value is a fixed offset from the eye turned by the entity's body yaw. Nothing of the pose is modelled: the rod is read where it is drawn. `HeldItemFeatureRendererMixin` (`require = 0`, priority 1500 so it runs after other mods' same-call `@Inject`s, e.g. Player Animation Library's and Animatium's item transforms) sits at `HeldItemFeatureRenderer.renderItem`'s `ItemRenderState.render` call, past its empty check, so once per non-empty held item of an armed entity: a small inlined gate (a player's hook was extracted this `HandPass` frame or the previous one, the state is a `PlayerEntityRenderState`, and its `id` together with the arm this item is drawn in is one of those hooks' owner keys: 1.21.4's `renderItem` gets no stack to tell a rod by, so these `(id, arm)` sets, filled at `updateRenderState` TAIL and by the draw-list walk below, keep other players and armour stands out) leads to the out-of-line read, which for the `getArmHoldingRod` rod of a player who is fishing (entity by `id`, `PlayerEntity.fishHook` is set on the client; the arm is re-checked against `getArmHoldingRod` **live**, since a key from the previous frame carries that frame's arm and could otherwise let the other hand's rod overwrite the right reading, and the rod itself by the live `getStackInArm`, which the item state was extracted from just before this drawing, nothing ticking in between) stores on the player (`AbstractClientPlayerEntityMixin`) the attachment point under the drawn pose, tagged with the pass (frame + the number of passes that have ended so far + either the buffer source or, for a drawing inside the world's entity loop, that loop: on 1.21.4 nothing is deferred and one `VertexConsumerProvider.Immediate`, the `GameRenderer`'s, takes every vanilla pass of a frame — the world's entities and block entities, the first-person hand, the screen effects, and the GUI's pictures such as the inventory's player model. Two optional hooks end a pass: `WorldRendererMixin` marks `WorldRenderer.renderEntities`' return (priority 1500, so a body other mods draw there — Freecam's Show Player — is still part of the entity pass; nothing marks its head, so First Person Model's body, drawn there, belongs to the pass that follows), and `VertexConsumerProviderImmediateMixin` counts `VertexConsumerProvider.Immediate.draw()`. The first keeps the GUI's pictures apart from the world's entities even when a mod replaces the buffer sources so vanilla's `draw()` never runs (ImmediatelyFast's `BatchableBufferSource` overrides it without calling super); the second separates passes that share one entity loop. Nothing inside `renderEntities` flushes, so a rod and a hook of the same entity loop stay in one pass; with neither hook applied no pass is ever matched, and every body-held line keeps vanilla's value. The collector alone would not do, because a mod may hand each entity its own — **Iris with a shader pack** does: its `entity_render_context/MixinEntityRenderDispatcher` `@ModifyVariable`s the buffer-source argument of every `EntityRenderDispatcher.render` into a freshly allocated `BufferSourceWrapper` as soon as a pack has set `WorldRenderingSettings.entityIds`, which nothing resets, so it outlives unloading the pack until the game restarts, and a rod and its hook never share one. What they do share is the loop: `WorldRendererMixin`'s head inject records the pass this entity loop opens in (frame + pass-end count) before the first entity, every drawing notes whether it happened while that record still held, and the match takes two such drawings of one loop as the same pass however their collectors differ. The pose is the loop's own `MatrixStack` either way, which is what the collector was ever a proxy for. Iris' shadow pass never goes through `renderEntities` and is drawn before the head records anything, so its drawings see the previous frame's record and note themselves as outside (it keeps pairing by collector, as before: its own one buffer source without a pack, per-entity wrappers with one); the GUI's pictures are past the loop's end mark and past every buffer-source flush, so their pass-end count differs; and without the optional head inject nothing is ever inside a loop and the match is the collector's alone, exactly as before. A body drawn inside `renderEntities` but into another collector is now matched where it used to fall back to the remembered spot — a glowing player or a spectator's outlines (`OutlineVertexConsumerProvider`), and a mod's own buffer source used inside that loop.). **Which of the two comes first is forced, by a second optional inject at `renderEntities`' head** (`ThirdPersonLineOrigin.sortBobbersLast`): the fishing bobbers are moved behind every other entity, both parts keeping their order, so the bodies are drawn first and every body-held line sits on the rod of this very frame. Vanilla 1.21.4 would not need it — `WorldRenderer.getEntitiesToRender` walks `ClientWorld.getEntities()`, i.e. the client's add order (`EntityIndex` keeps the entities in an `Int2ObjectLinkedOpenHashMap`), nothing sorts the list afterwards (there is no `ENTITY_COMPARATOR`; that entity-type-identity-hash sort existed only in 1.21.6–1.21.8), and a player is added before the hooks it casts. **Iris does.** Its `MixinLevelRenderer_EntityListSorting` (mixin priority 999, in `iris-batched-entity-rendering.mixins.json`, which is *not* gated on a shader pack being in use) wraps the `Iterable.iterator()` inside `getEntitiesToRender` and regroups every entity by `EntityType` through a `HashMap` so its entity batching sees one type at a time; `EntityType` inherits `Object.hashCode`, so which of the player and fishing-bobber groups lands first is an identity hash — arbitrary, fixed for the session, different in every launch. On 1.21.6–1.21.8 vanilla's own sort ran after Iris and the port's partition after that; here vanilla no longer sorts, so without the partition Iris would have the last word and, in about half of all launches with Iris installed, every hook would be drawn before every body for the whole session. The inject sits at the last named method before the loop, so it runs after anything that fills or reorders the list. It is an in-place stable partition — invisible to the rest of `WorldRenderer`, whose only other uses of the list are the F3 entity count (taken before it) and the `clear()` later in the same frame — and not a wrapper around Iris' or anyone's sort. Reordering is as close to free of consequence as the renderer allows: `entity_cutout` on the bobber's texture is opaque and depth-writing and `line_strip` blends but writes depth and carries alpha 255, neither is a `translucent` layer (so neither is quad-sorted at draw time), no translucent layer moves relative to another, a glowing bobber's outline copy carries the colour set for that entity right before it draws (`entity_cutout` does affect the outline, `line_strip` doesn't), and neither bobber layer has a dedicated allocator in `BufferBuilderStorage`, so a bobber costs its two draw calls wherever it sits and moving one contiguous run is worth at most one draw call at the seams, only ever one fewer — and with Iris' batching in front of it, a contiguous run moved to the end keeps every other type's grouping intact. What is left is the one pairing a reorder can decide: a bobber behind an entity layer that blends and writes depth, which `entity_translucent` does and every player body uses (`PlayerEntityModel`), so it is now always drawn after that body and depth-rejected; the layer's 0.1 alpha cutout and skins being alpha 0 or 255 make that a non-event. 1.21.4 does extract and draw each entity in turn (`EntityRenderDispatcher.render`), so an owner drawn before its hook isn't known from this frame yet — hence the previous frame's owner set, and hence every player's hook counting for it, not only a body-held one; and a hook whose owner is drawn before it would have no reading at all in the hook's very first frame. That is what the same head walk also does: it stamps the rod-reading gate with the owners of the bobbers it finds in the draw list, so a hook of the world's pass is read in the frame it appears, as on 1.21.9+ and 26.x. From 1.21.9 on, and on 26.x, vanilla extracts every entity before submitting any, so a hook's extraction always precedes its owner's rod and those branches gate on this frame alone; here the two are interleaved, and the draw list is that same knowledge one step early (every bobber in it is extracted a moment later in the loop this precedes). That is why the walk is unconditional and not itself gated: a gate would skip the one frame it is needed for. With no bobber in the list it is a type check per drawn entity and nothing else — no write, since the two indices never part, and no allocation; with one, every entity after it is written once, against the two reference stores per entity vanilla itself makes on that same `ArrayList` in the same frame (`getEntitiesToRender`'s `output.add` and the later `clear()`); and a bobber costs a field read, an `isRemoved()` test and an `instanceof` inside `getPlayerOwner` (1.21.4's projectiles hold their owner directly — no `LazyEntityReference`, no `Optional`), of which there are only ever a handful. With the held-item read it is one of the two places where the mod's cost scales with what is drawn, and the only one linear in *all* the drawn entities, at a fraction of a percent of the entity loop it precedes. A hook outside that list — Iris' shadow pass, or a body another mod draws at `renderEntities`' own head, before the walk gets there — still falls back for its first frame, to the last drawing of that rod or, failing that, vanilla's value. The owner, its partial tick and the same-pass-only flag ride on the hook's render state (set at `updateRenderState` TAIL, dropped at its `render`: on 1.21.4 one `EntityRenderer` keeps one render state for every entity of its type, for the client's whole life, so the last hook of a world would otherwise keep its owner — and its world — alive until the next hook is extracted; other mods keep render states past their frame too, as Iris' shadow pass keeps its last frame's, also after a disconnect); the pending offset is cleared once `h` is written and the last hook's pass (its buffer source) at the next frame's start (`GameRendererMixin`), so no static reference outlives its drawing or frame. At the hook's `render` HEAD, when the owner's rod was drawn earlier in the same pass, the line offset is that point through the inverse of the hook's pose (a pass that turns its root cancels out), minus the line's 0.25 lift. Otherwise it is the tip where the rod was last drawn, relative to the body's position and turned with its yaw (`LivingEntityRenderer.clampBodyYaw` mirrored), while the owner still holds a rod in that arm; a pose or mount change invalidates that offset, and it is kept anyway, because a one-frame lag is far less visible than a one-frame teleport — not because it is the closer of the two candidates. Usually it isn't: measured against the tip as drawn on the transition frame, vanilla's value is nearer for most of them (leaving gliding or a riptide spin 2.15 blocks or more for the kept reading against 0.12, waking 0.8–2.1 against 0.12, a crouch 0.54 against 0.07), and the kept reading only wins leaving swimming (1.04 against 2.12) and lying down (0.81 against 1.39); a mount change or a lean that ramps up is small either way. What the leniency buys is the frame the origin would otherwise jump to a different anchor and back, which is the visible artifact; in vanilla's own order this whole path is a fallback rather than the usual one. The yaw re-rotation follows the pose the reading was taken in, which is the convention the offset is in. The remembered offset carries the render offset of the frame it was read in (`EntityRenderer.getPositionOffset(S)`, which the pose includes and the body position it is measured against does not): it cancels while that offset holds, and a player's is the crouch shift, which the remembered path's pose gate keeps in step, plus the experimental minecart's lerp, which it does not — a frame of that lerp out on the fallback path, and still far nearer the rod than vanilla's guess. Re-deriving it would mean re-deriving a vanilla method any mod may override, at the reading and at the replay. An older reading isn't kept; else vanilla's value. A first-person line `FishingLineOrigin` left at vanilla's value (see its Javadoc) with the camera on the player takes only the same-pass rod, never the remembered one: no body is on screen, and the remembered spot (from an F5 view just left, or from Iris' shadow pass, whose entity collection doesn't skip the camera entity as `WorldRenderer`'s does and so draws the local body with its rod and its hook) would start the visible line at a rod that isn't drawn. Iris' shadow pass carries no line of its own: it exists only with a shader pack, and with one every entity render gets its own buffer source, so its rod and its hook never pair — nor does it go through `renderEntities` (it sorts its own list by the same identity hash), so neither the sort hook nor the loop tie reaches it. Player Animation Library's first-person body (drawn earlier in the world pass) still carries the line. With the camera on another entity vanilla never draws the local player, so a drawn body is a mod's and may come after the hooks (Freecam's Show Player draws it itself at `WorldRenderer.renderEntities`' TAIL, after every other entity): that line keeps the remembered spot. The remembered offset is taken whenever a hook of the pass gives the world position, before or after the rod (a mod may draw the body after the hooks). Exceptions disable it until the next world; without frame counting nothing is read.
- **`ThirdPersonRod`** — the body-held rod's attachment point in the space `HeldItemFeatureRenderer` submits the item in: the rod's tip (`RodSprite`; not first person's vanilla anchor, which sits by the tip only at first-person scale and angle) on the model mid-plane, through the `handheld_rod` `thirdperson_righthand` display transform (the left hand's is the same after `Transformation.apply`'s left-hand fix). Cached per frame.
- **`RodSprite`** — the tip of the `item/fishing_rod_cast` sprite, the rod model's source in every view (on 1.21.4 in the block atlas, which holds the item textures: `JsonUnbakedModel` resolves an item model's textures against `SpriteAtlasTexture.BLOCK_ATLAS_TEXTURE`, which is deprecated but is still the key `BakedModelManager.getAtlas` takes): a resource pack's redrawn sprite is measured (visible pixels at/above the item alpha cutout, unioned over animation frames; a shift beyond `MAX_TIP_SHIFT`, the one tuned constant in the rod geometry, is ignored as a misread), cached per `SpriteContents` identity, i.e. per resource reload. 1.21.4 has no `SpriteContents.isAnimated()`, so its private `getFrameCount()` stands in (`SpriteContentsAccessor`): it is `> 1` exactly when the sprite has an animation, and only then are the `getDistinctFrameCount()` tiles read instead of tile 0. The tile grid is not a substitute — an `.mcmeta` sizes the sprite even when its frame list collapses to a null animation, so a multi-tile image can be unanimated.
- **`FishingLineVisibility`** + `FishingBobberEntityStateMixin` / `FishingBobberEntityMixin` — hides the line (not the bobber) of a hook whose rod has left its owner's hands, in every perspective and for every player (MC-310980, MC-211561): the server removes such a hook only a tick plus the ping later, or never while the tick rate is frozen. Where `FishingLineOrigin` placed the line on the drawn first-person rod, it stays until the lowering rod is gone from the drawn items (a first-person line left at vanilla's value hides at once: vanilla would start it at the off-hand side, where no rod is). Only hooks whose owner was seen holding a rod (a flag on the hook) are hidden, so hooks cast by other items keep vanilla's line; for the local player a rod among the drawn items counts too (the own hook arrives a round trip after the cast). Decided at the end of `updateRenderState`, carried on the render state, applied by a `@WrapWithCondition` (MixinExtras v2) on `render`'s one `renderFishingLine` call site, which its loop reaches once per segment; an exception leaves lines visible until the next world or dimension. Hiding a line coexists with **Iris**, whose always-loaded `MixinFishingHookRenderer` appends one degenerate vertex to `line_strip` at this same method's second `pop()` (`require = 1`): the wrap removes no instruction, so Iris' point and both `pop()`s survive, and with the 17 segments skipped that lone vertex is duplicated by `BufferBuilder.endVertex` into a two-vertex strip whose zero normal the lines shader turns into a NaN position — nothing drawn, nothing thrown. In Iris' own `SegmentedBufferBuilder` one builder serves the whole pass per layer and `splitStrip()` is triangle-strip-only, so that vertex is the separator between hooks and removing a line's vertices changes nothing visible. The three `@ModifyVariable`s keep their ordinals under Iris' inject too: Mixin resolves every injection point in its `PREINJECT` pass before applying any, and Iris' point is after the three float stores in any case.
- **`HandPass`** + `GameRendererMixin` / `HeldItemRendererMixin` — whether the hand pass reached a hand last frame (frames counted at `GameRenderer.render`'s only `MinecraftClient.isFinishedLoading()` call, i.e. once per rendered frame, inside its `!skipGameRender` block, through which Dynamic FPS skips most frames while throttling (a skipped frame counted as one without a hand would put the line at vanilla's value), the frame marked where the five-argument `HeldItemRenderer.renderItem` calls `renderFirstPersonItem`, past any cancel; also reached while scoping, where nothing is drawn, so `FishingLineOrigin` checks scoping itself). No rod on screen → vanilla's value, whatever hid the hand (spectator, a mod cancelling the hand pass), unless the player's own body is drawn with the rod in the world pass (asleep, a third-person camera; Player Animation Library's first-person model mode, whose body counts only when drawn earlier in the same pass than the hook): then `ThirdPersonLineOrigin` puts the line on that rod. The HUD hidden with F1 is the exception: it hides the hand but not the line, a world object, so the line stays corrected where the rod would be. The frame counter runs before the camera update, which 1.21.4 does inside `renderWorld` (no separate `updateCamera`), so right after `renderWorld`'s `Camera.update` call (after the tick, before the entities and the hand pass) `HandPass` samples the live `GameOptions.hudHidden` (which `renderHand` reads later in the frame) and the rest of `renderHand`'s gate (first person, not rendering a panorama, awake, not spectating), plus the camera on the player, not in third person and at the player's eye where `Camera.update` puts it (some freecam mods keep the player as camera entity and don't move the camera into third person; the smoothed eye height comes through `CameraAccessor`). At the next frame's start it latches whether a hand is drawn when only the HUD decides, from frames that prove it (a drawn hand; a missing one with the HUD and the gate open means a mod hid it); a frame with the gate closed, or one that didn't render the world, restores the default (drawn). While the HUD is hidden (this or the previous frame) the line stays corrected if that latch holds and the gate is open this frame. So a hidden HUD never moves the line (Camerapture's photo frame and freecams on their own camera entity keep vanilla's value, unless they draw the player's body, as Freecam's Show Player, its default, does: then the body's rod, one frame late, from the remembered spot; freecams that move the player's camera into third person keep the body's rod; F5, sleep or spectator before F1 don't stick). Mods that keep the hand while hiding the HUD (Better F1) stay corrected through the normal path. These injects are `require = 0`: if the counter or the mark is blocked, the line just stays vanilla, and `FishingLineOrigin` logs one warning (frame counter never ran, or no hand mark seen while fishing in first person); without the sampling, F1 leaves vanilla's line.
- **`SpriteContentsAccessor`** — `@Accessor` for `SpriteContents.image` and `@Invoker` for its private `getFrameCount()`, which stands in for the `isAnimated()` 1.21.4 doesn't have. **`CameraAccessor`** — `@Accessor`s for `Camera.cameraY`/`lastCameraY`. **`GameRendererInvoker`** — `@Invoker`s for `GameRenderer.tiltViewWhenHurt`/`bobView`/`getFov`. **`GameRendererAccessor`** — `@Accessor`s for `GameRenderer.ticks` (the warp's spin counter; 1.21.5 replaced it with a `nauseaEffectTime`/`nauseaEffectSpeed` pair) and `fovMultiplier`/`lastFovMultiplier` (the movement FOV modifier, for the shared FOV factor). **`HeldItemRendererAccessor`** — `@Accessor`s for `HeldItemRenderer`'s drawn items and equip progress. **`VertexConsumerProviderImmediateMixin`** — counts `VertexConsumerProvider.Immediate.draw()` calls for `ThirdPersonLineOrigin`'s pass tag (`@ModifyExpressionValue`, `require = 0`, on the method's only field read, so nothing is allocated). **`WorldRendererMixin`** — two optional `@Inject`s on `WorldRenderer.renderEntities` (`require = 0`, mixin priority 1500 so both run after other mods' default-order injects at the same point, at the head as at the return): at TAIL it marks the pass's return for the same tag (a body other mods draw there is still inside the pass; the head is deliberately not marked as a pass end, so a body drawn there belongs to the pass that follows), which is what still separates the world's entities from the GUI's pictures when a mod replaces the buffer sources; at HEAD it moves the fishing bobbers to the back of the list vanilla is about to draw, so a fishing player's body precedes the hooks it cast (Iris regroups that list by entity type, so without this the order would be an identity hash), and stamps the rod-reading gate with the owners of the bobbers in it, so a hook is read in the frame it appears. **`FishingRodFix`** — the shared logger, `isRod` and `holdsRod`.

Declared incompatible: Enchanted Fishing Line (`enchanted_fishing_line`, all versions) is listed under `breaks` in `fabric.mod.json`, so the loader refuses to start with both and shows its incompatible-mods screen. On a player's body (third person): the rod is read where `HeldItemFeatureRenderer` submits it, so everything that poses the body, arm or item before that call is followed (animation mods, held-item position mods, First Person Model's offset body, Mine Little Pony's ponies), but not what changes the item after it (a resource pack's changed `thirdperson` display transform, per-item or 3D rod models, Animatium's 1.7 stick rod, a wrap, redirect or argument change of that call, or a same-call `@Inject` above priority 1500; Animatium can also cancel a sleeping player's body render and force the cast rod model on or off, so the drawn sprite may not be `item/fishing_rod_cast`), nor rods drawn outside the pass the hook's line is drawn in (Mine Little Pony's magic ponies with third-person magic; a player with the glowing effect and a spectator's outlines, whose body goes into the outline buffer source while its hook stays in the entity one, are inside that pass and matched, since both are drawings of the same entity loop; Real Camera 0.6.2-beta-1.21.4 has no fishing-renderer mixin and doesn't change the camera type, but cancels `renderHandsWithItems` while it renders: with the camera still on the player the first-person line keeps vanilla's value, and its binding mode, the default, replays its own recorder — a different collector, but inside the entity loop, so the loop tie now matches it and its line gets the remembered spot one frame late instead of staying vanilla (verified on Real Camera 0.7.4-beta-1.21.8, whose binding mode re-emits the caught positions into the pass's own buffer source in the pass's space; this branch's 0.6.2 build not re-read) — while its classic mode draws the body into the level's buffer source after the hooks and gets the remembered spot one frame late) or not through that feature renderer (morph mods such as Woodwalkers: vanilla's value). Mine Little Pony's magic now starts the line at the glow copy's tip rather than at vanilla's value: its `HeldItemFeature` draws the item three times for one arm — the real one, then two glow copies through its own wrapped vertex-consumer provider — all three inside the entity loop with the same `MatrixStack`, and the reading is last-write-wins, so the glow copy is what gets stored and the loop tie matches it (a fraction of a block from the real levitating rod, and far closer than vanilla's guess; verified on Mine Little Pony 4.14.4+1.21.7, this branch's build not re-read).21.4 it carries no fishing-renderer mixin at all, so a pony's ordinary rod is read with the pony pose. Likewise Freecam with Show Player off (its own camera entity, the body hidden) starts the line where the hidden body's rod was last drawn while the pose matches, e.g. after an F5 view (checked on Freecam 1.3.2+mc1.21.4, the only 1.21.4 build: with Show Player on, its default, the body is drawn at `WorldRenderer.renderEntities`' TAIL at the default injector priority, i.e. inside the entity pass but after the hooks, so that line takes the remembered spot one frame late). Where the owner's rod isn't drawn in the pass before its hook (the owner out of view, a hook that arrived before its owner, a body drawn after the hooks), the line starts where it was last drawn, turned with the body; a changed arm pose (a swing) shows when the rod is drawn again, a pose or mount change is followed only as far as a reading from the previous frame allows (one frame of pose change, then the next drawing settles it), and a player never seen with the rod drawn, or in another pose for more than a frame, keeps vanilla's value until it is drawn again (a jump then); a player who starts drawing another way in the same pose while fishing (a morph mid-cast) keeps that remembered spot. A rod hidden by another mod (Not Enough Animations' off-hand hiding) leaves the line where the rod was last drawn; hidden in bed (its default) the line keeps vanilla's value unless the rod was seen drawn in bed before. The state's `pos` keeps vanilla's value for a body-held rod, so a mod that reads it sees that. A body drawn at `renderEntities`' own head, before the pass is recorded, is outside the window — First Person Model injects there at the default priority, below the port's — so with an Iris shader pack, where the collector no longer ties anything, its body is the one inside the loop the fix does not reach (without a pack the shared buffer source still matches it). A mod rendering the world twice per frame into one buffer source without flushing it in between could hand one pass's rod to the other (vanilla's passes each end with a `draw()`, which ends a pass here). A hook drawn before its owner has no reading of this frame's rod: its line is one frame late for as long as that order holds (visible on a fast arm swing; a pose or mount change keeps the previous frame's reading rather than falling back to vanilla, so the origin never jumps to a different anchor for a frame — the lag is largest leaving swimming, gliding or a riptide spin and when lying down or waking), and a line `FishingLineOrigin` left at vanilla's value with the camera on the player (Player Animation Library's first-person body) keeps vanilla's value, since that case takes only a rod drawn earlier in the same pass. The bobbers-last inject (see the Architecture section) is what keeps that from being the normal case: vanilla's own order already puts a body first, but **Iris regroups the drawn entities by entity type through a `HashMap` whenever it is installed**, shader pack or not, which would otherwise make the order an identity hash — arbitrary per launch and fixed for the session. A mod that keeps that mixin from applying, draws the entities without going through `renderEntities`, or re-orders the list from a head inject of a still higher mixin priority brings that coin toss back; on the losing side every body-held line is one frame late, and a newly cast hook also loses its first frame (the same head walk is what stamps the rod-reading gate). What no draw order can fix is a hook the server sent before its owner, a body another mod draws after the hooks (Freecam's Show Player), and a hook whose pass the walk never sees (Iris' shadow pass, whose own list is sorted by the same identity hash) — all of them fall back the same way. The inject only orders the entities `WorldRenderer` itself draws.

## Dev environment gotcha

Loom writes `.idea/runConfigurations/Minecraft_Client.xml` only when it is missing and never updates it, and `.idea` is shared by every branch of the checkout. A stale config on the 26.3 branch lacks `-XX:StackShadowPages=32` (from Mojang's version JSON), and the client then dies natively on an in-world resource reload (access violation in `jvm.dll`, no `hs_err`). A 26.x config on an old branch fails to start on JDK 21 (`--sun-misc-unsafe-memory-access`). After switching version families, delete the XML and run `./gradlew ideaSyncTask`.

## Versioning

Each Minecraft version lives on its own branch (e.g. `1.21.4`, `1.21.11`, `26.3`). The version numbers in `gradle.properties` (`minecraft_version`, `loader_version`, `loom_version` — on branches not yet ported to the current fix the Loom version sits in `build.gradle`'s `plugins` block instead — and `yarn_mappings` on pre-26 branches) must be updated together when porting to a new MC version. The `mod_version` in `gradle.properties` is independent of MC version.

## Roles

Project roles:

- `/port-version <mc_version>` — ports the mod (the current reference fix from the default branch) to a target Minecraft version, backport or forward-port. It reviews the port in rounds with `/reviewer` (correctness and performance per round, compatibility once in parallel) until no real bug is left, fixes the rest, and only then launches the game. See `.claude/skills/port-version/SKILL.md`.
- `/reviewer [scope] [--only <dimensions>] [notes]` — read-only, one-pass review of the branch's unpublished changes (or a range, paths, or `all`). Fresh reviewer agents check the default review, a performance gate (the mod's cost within noise of zero on a whole frame's budget) and compatibility with known mods, shader packs and resource packs; the findings are verified and returned as one report. It never edits, builds or commits. See `.claude/skills/reviewer/SKILL.md`.
