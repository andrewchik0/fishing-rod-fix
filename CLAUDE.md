# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A client-side Fabric mod for Minecraft that fixes vanilla bugs where the fishing line starts in the wrong place. In first person the line origin is placed on the rod the hand pass actually draws, at the drawn rod model's tip, where the line leaves it (the model the game draws: resource-pack 2D/3D models and display transforms, server item models, modded `FishingRodItem`s): across aspect ratios, world and hand FOV, the rod's equip dip, swing and sway, view bob, hurt tilt and nausea warp, the camera's smoothed eye height, and resource packs that redraw the rod. On a player's body (third person, other players, sleeping in any view) it is placed on the tip of the rod the body is drawn holding, in whatever pose the model is in.

Each Minecraft version lives on its own branch and the code differs per version family (see Versioning). This branch targets **MC 26.3** (unobfuscated, official Mojang names).

## Build Commands

```bash
# Build the mod (produces JARs in build/libs/)
./gradlew build

# Run the Minecraft client with the mod loaded
./gradlew runClient

# Generate sources and set up IDE
./gradlew genSources
```

CI builds with Java 25 (`release 25`); run Gradle on a JDK 25 for 26.x branches.

## Architecture (26.3)

Purely client-side; no access widener and no Fabric API dependency, and MixinExtras is not bundled either: the loader's own copy has `injector.v2.WrapWithCondition` from 0.15.7 on, and the `JAVA_25` compatibility level needs sponge-mixin 0.16+ (Fabric Loader 0.17.0) — both far under the declared floor `>=0.19.0`. That floor is therefore above the minimum that merely *loads* — measured on 26.3: with the floor hand-lowered, the jar runs on Fabric Loader 0.18.6 and 0.17.2 with all ten mixins of that jar applying (the config has grown since; the additions are plain `@Accessor`s, `@Inject`s and a MixinExtras MEV) — and it is kept where it is on purpose, because `depends.fabricloader` also picks the Mixin behaviour set the loader applies to this mod (`FabricMixinVersions` on loader 0.19.5 — older loaders carry fewer rows: `>=0.19.4` → 0.17.4, `>=0.19.0` → 0.17.1, `>=0.18.4` → 0.17.0, `>=0.17.3` → 0.16.5, `>=0.16.0` → 0.14.0, `>=0.12.0` → 0.10.0): below Fabric compat 0.17.1 a mixin's injectors are prepared through `INJECT_PREPARE_LEGACY`, so lowering the floor is a behavioural change, not a metadata tweak. Nothing is asking for it on this line either: Fabulously Optimized for this MC version pins Fabric Loader 0.19.5. A Jar-in-Jar MixinExtras copy would lower nothing. (The 1.20 branch, at `JAVA_17`, does bundle MixinExtras — there it drops the floor from `>=0.15.7` to `>=0.14.25`.)

- **`FishingHookRendererMixin`** (`src/client/java/.../mixin/client/`) — `@ModifyExpressionValue` (`allow = 1`) on the only `Vec3.add(Vec3)` in `FishingHookRenderer.getPlayerHandPos`, i.e. the result of vanilla's first-person branch: delegates to `FishingLineOrigin`, or keeps vanilla's value while vanilla draws the player's own body (asleep, or a detached camera), whose rod `ThirdPersonLineOrigin` takes. Where `FishingLineOrigin` keeps vanilla's value with the camera on the player, it tells `ThirdPersonLineOrigin` (a flag reset at `extractRenderState` HEAD), whose line then only moves onto a body drawn earlier in the same pass. The third-person branch isn't hooked: players other mods send down it (First Person Model, Real Camera) get the body-held rod too. An MEV (`require = 0`) on the method's first-statement `getHoldingArm` call (allocation-free, value unchanged) notes that vanilla's method body ran: when a mod replaced it at HEAD (Vivecraft: the local player's controller in VR, a remote standing VR player's tracked hand; Mine Little Pony: every pony in third person), `ThirdPersonLineOrigin` only moves that line onto a body drawn earlier in the same pass, never onto a remembered spot. It sits in the body, not at RETURN, because a cancelling RETURN inject (First Person Model's offset) would skip a RETURN injector applied after it. Without it every body-held line is same-pass only. It also holds the line-visibility injectors (`extractRenderState` HEAD and TAIL, `@WrapWithCondition` in `submit`) and the body-held line's placement at `submit` (`require = 0`): a HEAD inject that works the offset out and three `@ModifyVariable`s at the STORE of `submit`'s float locals 0–2 (`xa`/`ya`/`za`) that write it, so nothing is allocated and `lineOriginOffset` keeps vanilla's value.
- **`FishingLineOrigin`** — replaces vanilla's guess (it doesn't reuse vanilla's eye-based vector): reads the state vanilla extracted for this frame's hand pass, takes the rod's line attachment point from `FirstPersonRod`, applies vanilla's item sway and own view bob/hurt tilt (`GameRendererInvoker`), and places the world point, relative to the camera and with the world-only nausea/portal warp undone, on the pixel where the hand pass draws that point. The world FOV comes from the extracted world projection's `m11` (in vanilla the camera's FOV), so mods that change the projection itself are followed too; an orthographic projection keeps vanilla's value. The rod's hand comes from the drawn items; while a rod is held but none is drawn yet (a quick F-swap with a hook out) the line stays with the hand it was last drawn in. All inputs are the frame's, so the origin is worked out once per `HandPass` frame and reused by later extractions of the local player's hooks in it (Iris' shadow pass extracts them again). Its class Javadoc lists the steps and every case that keeps vanilla's value.
- **`FirstPersonRod`** — the first-person rod's attachment point, in the hand pass's view space: the drawn model's tip (`RodModel`, gripped where a held rod's third-person display transform puts the hand: the same arm's, else the other arm's, else a tip measured for that model; the drawn items lag the inventory through a swap and draw the rod uncast), through the display transform the item is drawn with (read from the hand pass's item state, left hand included), then `applyItemArmTransform` (incl. the equip dip) and `swingArm`, both arms modelled with vanilla's `invert`. Every rod, vanilla's included, takes the line from `RodModel`'s point (user decision 2026-09-26: no vanilla screen-anchor calibration, which put the vanilla line ~1.3 texels beside the tip and left a gap on rods whose tip fell near vanilla's).
- **`ThirdPersonLineOrigin`** + `ItemInHandLayerMixin` / `AbstractClientPlayerMixin` — the line origin on a rod held by a player's body, for every line not on the first-person rod: vanilla's third-person branch for every player (MC-4490 crouch, MC-176514 riding, MC-198777 boat, MC-247425 arm swing, MC-270173 swim/crawl, MC-270174 sleep; also walking, gliding, riptide, death), and the local player whose body is drawn in first person (asleep, a mod-detached camera, a mod drawing it such as Player Animation Library's first-person model mode). Vanilla's third-person value is a fixed offset from the eye turned by the entity's body yaw. Nothing of the pose is modelled: the rod is read where it is drawn. `ItemInHandLayerMixin` (`require = 0`, priority 1500 so it runs after other mods' same-call `@Inject`s, e.g. Player Animation Library's and Animatium's item transforms) sits at `ItemInHandLayer.submitArmWithItem`'s `ItemStackRenderState.submit` call, past its empty check, so once per non-empty held item of an armed entity: a small inlined gate (a body-held hook was extracted this `HandPass` frame, the state is an `AvatarRenderState`, the stack a rod) leads to the out-of-line read, which for the `getHoldingArm` rod of a player who is fishing (entity by `id`, `Player.fishing` is set on the client) stores on the player (`AbstractClientPlayerMixin`) the attachment point under the submitted pose, tagged with the pass (collector + frame; valid while a collector serves one pass per frame, as vanilla's level pass, its picture-in-picture renderers and Iris' shadow pass each do with their own storage). The owner, its partial tick and the same-pass-only flag ride on the hook's render state (set at `extractRenderState` TAIL, dropped at its `submit`: other mods keep render states past their frame, as Iris' shadow pass keeps its last frame's, also after a disconnect, and the owner would keep its world alive); the pending offset is cleared once `za` is written and the last hook's pass (its collector) at the next frame's start (`GameRendererMixin`), so no static reference outlives its submit or frame. At the hook's `submit` HEAD, when the owner's rod was drawn earlier in the same pass (entities submit in the client's add order, owner before the hooks it casts), the line offset is that point through the inverse of the hook's pose (a pass that turns its root cancels out), minus the line's 0.25 lift. Otherwise it is the tip where the rod was last drawn, relative to the body's position and turned with its yaw (`solveBodyRot` mirrored), while the owner still holds a rod in that arm and is in the same pose and riding state (a drawing that can't be read as a rod, e.g. a mid-cast swap to an unreadable model, drops that memory; one not measured yet this frame keeps it); else vanilla's value. A first-person line `FishingLineOrigin` left at vanilla's value (see its Javadoc) with the camera on the player takes only the same-pass rod, never the remembered one: no body is on screen, and the remembered spot (from an F5 view just left, or from Iris' shadow pass, whose entity extraction doesn't skip the camera entity as `LevelExtractor.extractVisibleEntities` does and so draws the local body with its rod, then the hook) would start the visible line at a rod that isn't drawn. The shadow's own line still sits on the shadow body's rod, and Player Animation Library's first-person body (drawn earlier in the level pass) still carries the line. With the camera on another entity vanilla never draws the local player, so a drawn body is a mod's and may come after the hooks (Freecam's Show Player adds it at `extractVisibleEntities` RETURN): that line keeps the remembered spot, as Real Camera's classic mode does. The remembered offset is taken whenever a hook of the pass gives the world position (also for a rod drawn after its hook, as Real Camera's classic mode does). Exceptions disable it until the next world; without frame counting nothing is read.
- **`ThirdPersonRod`** — the body-held rod's attachment point in the space `ItemInHandLayer` submits the item in: the drawn model's tip (`RodModel`) through the display transform and item-definition transform the item is drawn with, both read from the submitted `ItemStackRenderState`. Cached per drawn model, transform and hand side (`DrawnItem`, 32 entries, least recently read replaced).
- **`RodModel`** — the rod as drawn: reads the item's resolved layers (`ItemStackRenderStateAccessor`, `LayerRenderStateAccessor`): the baked quads and the `ItemTransform`/local transform `LayerRenderState.applyTransform` draws them with, so resource-pack models (2D, 3D, per-`display_context`, enchanted variants), server `item_model`/`custom_model_data`, CIT-style model swaps and modded rods are what is measured. Only visible geometry counts: a generated model (every quad within `ItemModelGenerator`'s z 7.5-8.5/16 slab, and per layer a SOUTH and a NORTH face over the whole canvas whose UVs span the whole sprite, u rising with x and v falling with y on both; anything else, and generated layers at different resolutions, goes to the 3D path) is measured on its sprites' pixels at/above the item alpha cutout (`SpriteContentsAccessor`): the rod's pixels are those shown in most animation frames (an effect flickering over it, like FurfSky's phantom rod's wisp flying along the line, isn't rod), the drawn line's those the uncast model shows in any frame and the cast model in none (the line may itself be animated); a 3D model on its visible texel cells: every face split into cells a 16x texel a side (1/16 block), each a box around its part of the (possibly rotated) face, kept where its part of the texture (bilinear over the quad's own UVs, read on at most 4x4 texels) shows a texel at/above the cutout, so a transparent placeholder element (glowing-3d-tools' line) or the empty part of a plane a bend is painted on (mb3d-items-pack) is no rod; faces whose whole texture rectangle is transparent (read on at most 8x8 texels) are dropped first. Where the line leaves the rod is read from the artist's uncast rod: the same stack resolved with no owner (so `fishing_rod/cast` is false) is compared with the drawn cast model; what the uncast model draws in any frame and the cast model in none is the line (pixels; 3D cells no cast cell shown in any frame occupies, matched by quantised boxes, so a line painted only on the uncast texture of shared geometry counts; only uncast quads not drawn exactly as a cast one — same corners, UVs and sprite — are cut into cells, which saves re-reading an uncast model identical to the cast one). A sprite: where the line's pixels touch the cast rod (8-neighbourhood), the end a contact is nearest to in BFS steps along the rod (ends from a double sweep over the rod's connected pixels, on the largest piece a contact lies on; the drawn line may also touch the rod lower down, at the reel: berserker-tools-weapons; on a tie, the end nearer the contacts overall); no contact: the pixel farthest from the grip (the origin of the third-person pose through the inverse display transform) among the pixels connected to it. A 3D model: the rod is the largest connected part of the cast cells (cells sharing a half-texel bucket, the grid offset by a quarter texel so texel-aligned faces fall inside buckets: touching cells join, cells half a texel or more apart don't, closer counts as touching; linear in the cells, no pair tests — pair tests cost 115-150k steps on dense voxel-style models such as faithful-3d), its ends the farthest pair of cells (a double sweep over cell centres), and the end farther from the grip is taken: a rod is held at one end and cast from the other (over the 2026-09-27 test set the far end is at least 1.42x as far from the grip as the near one; choosing by the drawn line instead picked the reel on moose-items and just-3d-stuffs, whose lines run down to the reel). A grip less than 1.35x farther from one end (`GRIP_RATIO`; 1.02-1.28x on packs with only pre-1.9 `thirdperson`/`firstperson` display keys, which 26.3 ignores, so the model is held by its centre: wolion-3d-64px-standalone, the-death-pack) tells neither, and the upper end (model y) is taken: rods are modelled tip up. The line starts at that end's extreme tip: the centre of its last texel (of the most-steps pixels, the one farthest in a straight line from the other end; vanilla: texel (14, 1)), or the mean of the rod cells' centres within a texel of the farthest along the end-to-end axis, as players know the vanilla line; unless the tip isn't ahead of where the drawn line meets the rod (80° or more off the rod's direction from the contact nearest that end — 3D: the centre of the rod's cell nearest the line's cell nearest the end: a decoration beside the line, e.g. Tide's crystal rod, Hypixel+'s yeti rod), then at that contact (user decision 2026-09-26; over the test set ordinary rods measure 0-69°, decorated ones 92° and up). Cost: one measurement per frame (another model in the same frame gets `DEFERRED`, vanilla's value, and is measured on a later frame). Ordinary rods take a few thousand steps, 3D models up to ~125k (texel reads, 3D cells and bucket entries; measured 2026-09-27: faithful-3d's 1134 quads ~12.5k, HD custom-model-data staves with large, mostly transparent painted planes 50-125k, ~3-5 ms, nearly all of it reading their empty cells; ~35-200 ns a step; measured in game: 16x sprites ~0.2-0.4 ms, a 512x sprite ~0.6-0.9 ms, 3D models with 600-700 visible cells ~0.6-1.4 ms). The cap is 200k steps, so a very complex model may take a few ms once (user decision 2026-09-26: accuracy over a one-off frame); over it: vanilla's value. A sprite is walked on a grid of at most 32x32 cells, every unique animation frame read per cell (exact up to 32x; larger sprites, or cells × the cast and uncast sprites' frames past 20k (`GRID_BUDGET`), on a coarser grid, one sampled texel per cell, the end cell then refined to its texel in two steps; the uncast grid is sized with the cast one, and one that can't be built (another canvas size) only drops the line comparison), at most 2048 quads. The first, cold runs happen at world join and dimension change behind the loading screen: `MinecraftMixin` (`setLevel` TAIL, `require = 0`) runs `RodModel.warmUp`: the pack's uncast vanilla rod (cached, so measured once per model: ~2 ms cold for a generated rod, ~9-13 ms for a 3D pack's) and, once per session, the 3D path on at most 8 of its faces (~0.5-4 ms cold; measured 2026-09-27); the first cast still measures the cast model, warm. A failed warm-up is logged once. The uncast re-resolve failing (an item model that needs an owner) only drops the uncast comparison. No readable geometry (a special renderer, empty quads, layers with differing transforms; checked cheaply each frame, not cached), a degenerate transform, over budget, or an exception (logged once; e.g. a closed sprite image): null, cached, and the caller keeps vanilla's value for that model until the next reload. Cached per the first layer's baked `ItemQuads` identity and grip (128 weak entries, least recently used replaced; so two stacks differing only in an overlay layer or in their uncast model share one tip, rare); `FirstPersonRod` and `ThirdPersonRod` also cache the final anchor per drawn model, transform and hand side (`DrawnItem`), so a frame that hits does compares only.
- **`FishingLineVisibility`** + `FishingHookRenderStateMixin` / `FishingHookMixin` — hides the line (not the bobber) of a hook whose rod has left its owner's hands, in every perspective and for every player (MC-310980, MC-211561): the server removes such a hook only a tick plus the ping later, or never while the tick rate is frozen. Where `FishingLineOrigin` placed the line on the drawn first-person rod, it stays until the lowering rod is gone from the drawn items (a first-person line left at vanilla's value hides at once: vanilla would start it at the off-hand side, where no rod is). Only hooks whose owner was seen holding a rod (a flag on the hook) are hidden, so hooks cast by other items keep vanilla's line; for the local player a rod among the drawn items counts too (the own hook arrives a round trip after the cast). Decided at the end of `extractRenderState`, carried on the render state, applied by a `@WrapWithCondition` (MixinExtras v2) that skips the `lines` geometry in `submit`; an exception leaves lines visible until the next world or dimension.
- **`HandPass`** + `GameRendererMixin` / `FirstPersonHandsAndItemsRendererMixin` — whether the hand pass reached a hand last frame (frames counted at `GameRenderer.extract`, the frame marked where `submitHandsWithItems` calls `submitArmWithItem`, past any cancel; also reached while scoping, where nothing is drawn, so `FishingLineOrigin` checks scoping itself). No rod on screen → vanilla's value, whatever hid the hand (spectator, a mod cancelling the hand pass), unless the player's own body is drawn with the rod in the level pass (asleep, a detached camera; Player Animation Library's first-person model mode, whose body counts only when drawn earlier in the same pass than the hook): then `ThirdPersonLineOrigin` puts the line on that rod. The HUD hidden with F1 is the exception: it hides the hand but not the line, a world object, so the line stays corrected where the rod would be. At each frame's `extract` (after the tick and the camera update) `HandPass` samples the live `Hud.isHidden()` and the rest of `renderItemInHand`'s gate (a player, first person, not panoramic, awake, not spectating), plus the camera on the player, not detached and at the player's eye where `Camera.alignWithEntity` puts it (some freecam mods keep the player as camera entity and don't detach; the smoothed eye height comes through `CameraAccessor`). It latches whether a hand is drawn when only the HUD decides, from frames that prove it (a drawn hand; a missing one with the HUD and the gate open means a mod hid it); a frame with the gate closed restores the default (drawn). While the HUD is hidden (this or the previous frame) the line stays corrected if that latch holds and the gate is open this frame. So a hidden HUD never moves the line (Camerapture's photo frame and freecams on their own camera entity keep vanilla's value, unless they draw the player's body, as Freecam's Show Player, its default, does: then the body's rod, one frame late, from the remembered spot; freecams that detach the camera from the player keep the body's rod; F5, sleep or spectator before F1 don't stick). Mods that keep the hand while hiding the HUD (Better F1) stay corrected through the normal path. Both injects are `require = 0`: if blocked, the line just stays vanilla, and `FishingLineOrigin` logs one warning (frame counter never ran, or no hand mark seen while fishing in first person).
- **`ItemStackRenderStateAccessor`** / **`LayerRenderStateAccessor`** — `@Accessor`s for an item's resolved layers (see `RodModel`). **`LevelRendererMixin`** / **`LevelRendererEndMixin`** — note the collector the level pass submits its entities to, at `LevelRenderer.submitEntities` HEAD and TAIL (`require = 0`, once per pass; the end at priority 1500, after other mods' injects at that return, which still belong to the loop): a rod reading through a known forwarding wrapper of it is tagged with the pass's own collector: Customizable Player Models' per-player wrapper (class under `com.tom.cpm.`) and Real Camera's binding-mode `RoutingSubmitCollector` (it forwards items to the level collector unchanged). Any other collector keeps its tag. **`DrawnItem`** — a cache key for a drawn item (quads and `ItemTransform` identity, hand side, local transform) that compares without allocating. **`SpriteContentsAccessor`** — `@Accessor` for `SpriteContents.originalImage` (`RodModel`'s pixel reads). **`MinecraftMixin`** — the measurement warm-up at `setLevel`. **`CameraAccessor`** — `@Accessor`s for `Camera.eyeHeight`/`eyeHeightOld`. **`GameRendererInvoker`** — `@Invoker`s for `GameRenderer.bobHurt`/`bobView`. **`FishingRodFix`** — the shared logger, `isRod` and `holdsRod`.

Known limitations: a sprite rod's line end is read from the uncast model's drawn line (else the point farthest from the grip), so a pack whose uncast line touches the rod elsewhere than where the cast line should leave it, or whose uncast model differs from the cast one in more than the line, can pick the other end; a 3D rod's is the end farther from the grip (the upper end when the grip is about as far from both), so a model held at its middle whose tip points down picks the wrong end; a rod drawn with a gap (dotted, segmented) ends at the gap; a model drawn by a special renderer (or a Fabric renderer mesh without baked quads) keeps vanilla's value, as does a model whose layers are drawn with different transforms, or one too complex to measure within the step budget; mods that re-pose the hand, or change the item it draws, in the renderer without touching its extracted state (viewmodel mods such as ViewModel, ScaleMe, Smallhands, Fancy View Model (a pose-stack offset/rotation/scale at `submitArmWithItem`'s `pushPose`, identity by default), Animatium's legacy item positions, CameraTweaks' first-person freelook, Inspect Animations; the drawn item: Animatium's equip animation, which passes its own main-hand stack to the per-hand call), shaderpack hand sway, portal-view mods that move the camera (Immersive Portals), Polytone line offsets and Tide's own hook renderer are not covered; mods that bob or sway the hand and world passes differently (BetterHandBobbing, View Bobbing Options, No Screen Bobbing, Tweakeroo's world view-bob toggle, ShakeTweaks' bob toggles and "Disable Hand View Sway"), and Clearviews with "Disable Nausea" turned off, leave the same mismatch vanilla has; mods that drop the nausea warp without Clearviews' mod id (anti-nausea in Meteor, Wurst, LiquidBounce) make the line swing around the rod under nausea/portal, and Clearviews with Iris shaders would do the same on 26.x, whichever of their warp wrappers won the load order (Clearviews `@WrapOperation`s `renderLevel`'s `Matrix4f.rotate` ordinals 0/1 and `scale(FFF)`, Iris' `MixinModelViewBobbing` the same instructions, both at default priority) — hypothetical for now, since Clearviews has no 26.3 build (latest 2.1.7+26.2); mods that extract a frame without rendering it (sbsshot's stereo screenshots) leave that shot, and the next frame, with vanilla's line; mods that hide one arm by cancelling its `submitArmWithItem` (Hide Hands, Exposure), or only its item (Player Animation Library during a first-person transition), leave the line at the hidden rod's tip, as do mods that hide the hand only after F1 was pressed (Camerapture's camera, Snapmatica's viewfinder, Picture Mode); conversely a mod that stops hiding the hand while F1 is on (Snapmatica's viewfinder or a freecam parked at the eye) leaves vanilla's line until F1 is released; camera-smoothing mods (SmoothCamera) drop the F1 line to vanilla's value during their F5/teleport glide; a local cast followed by a slot switch before the hook reaches the client, on a ping longer than the drawn items' few-tick lag, keeps vanilla's line until the server removes the hook. On a player's body (third person): the rod is read where `ItemInHandLayer` submits it, so everything that poses the body, arm or item before that call is followed (animation mods, held-item position mods, First Person Model's offset body, Mine Little Pony's ponies), but not what changes the item after it (a wrap, redirect or argument change of that call, or a same-call `@Inject` above priority 1500; the model and display transform the item is drawn with are read); a pose that collapses the item (scale 0, Customizable Player Models' never-shown item slot) isn't read; in a pass outside the level pass's entity loop (Iris' shadow pass) a player whose collector Customizable Player Models wraps is read in the wrapper's pass, which no hook matches, so that shadow's line keeps the remembered spot, nor rods drawn outside the level pass's collector (Mine Little Pony's magic ponies with third-person magic; Real Camera's binding mode is read through its router, see `LevelRendererEndMixin`) or not through that layer (morph mods such as Woodwalkers: vanilla's value). Mine Little Pony's magic keeps vanilla's or Mine Little Pony's value, and Mine Little Pony places every pony's line itself (a `getPlayerHandPos` HEAD cancel), so a pony's line moves only onto its rod drawn earlier in the same pass and otherwise keeps Mine Little Pony's value; Punchy (26.3, 2.8b) replaces `getPlayerHandPos` at HEAD for the local player in first person with its own animated rig's grip, so the first-person line is Punchy's (off its rod at other aspect ratios and FOV modifiers, and off the vanilla rod it draws when disabled in its config, for blacklisted rods and during its vanilla-hand equip window); only a body rod drawn earlier in the same pass (asleep, detached camera, Iris' shadow) moves it, and third-person lines are corrected as usual; Animatium's 1.7 mode (not its default) swaps the third-person rod for a stick model, which is read, but whose line end the uncast comparison (against the rod) can't tell, and its 1.7/1.8 rod versions translate the first-person rod inside `LayerRenderState.applyTransform`, which `RodModel.display` (applying `ItemTransform` itself) doesn't see; Real Camera's binding mode submits the body at `submitEntities`' return, after the hooks, through a `RoutingSubmitCollector` that forwards items to the level collector: the reading is re-tagged with the level pass (`LevelRendererEndMixin` ends the loop after that inject) and remembered through the hook's pose, so its line starts on the drawn rod one frame late (a first frame, or a changed pose, keeps the previous spot or vanilla's value). Likewise Freecam with Show Player off (its own camera entity, the body hidden) can start the line where the hidden body's rod was last drawn (an F5 view, Iris' shadow pass) while the pose matches. Where the owner's rod isn't drawn in the pass before its hook (the owner out of view, a hook that arrived before its owner, a body drawn after the hooks), the line starts where it was last drawn, turned with the body (except a reading taken asleep, which is in the bed's space: vanilla turns a sleeping body by the bed's direction, not by the body yaw, so that reading is used unturned), while the pose and riding state match; a changed arm pose (a swing) shows when the rod is drawn again, and a player never seen with the rod drawn, or in another pose since, keeps vanilla's value until it is (a jump then); a player who starts drawing another way in the same pose while fishing (a morph mid-cast) keeps that remembered spot. A remembered spot is relative to the body's position, so it also carries the offset the reading frame drew the body at (`AvatarRenderer.getRenderOffset`): the crouch shift, which the pose gate keeps in step, and, for a passenger of an experimental-movement minecart, that frame's cart lerp correction, a fraction of a block until the rod is drawn again. A rod hidden by another mod (Not Enough Animations' off-hand hiding, Essential's cosmetics and emotes with `hidesHeldItems`, Figura's `vanilla_model` item hiding) leaves the line where the rod was last drawn; Figura's item pivots draw the rod themselves after cancelling the layer, so that line keeps a remembered spot or vanilla's value; spectating a fisher in first person in a replay (Flashback, Replay Mod) sends vanilla down its third-person branch for a `RemotePlayer`, so the line keeps the remembered body-rod spot or vanilla's value, off the drawn first-person rod as in vanilla; hidden in bed (its default) the line keeps vanilla's value unless the rod was seen drawn in bed before. `lineOriginOffset` on the hook's render state keeps vanilla's value for a body-held rod, so a mod that reads it sees that. A mod rendering the level twice per frame into one collector (portal mods on older versions) could hand one pass's rod to the other. Declared incompatible: Enchanted Fishing Line (`enchanted_fishing_line`, all versions) is listed under `breaks` in `fabric.mod.json`, so the loader refuses to start with both and shows its incompatible-mods screen. It has no 26.3 build yet; the entry is pre-emptive, matching every other branch. Its builds elsewhere (1.0.0 for 26.2 and 26.1–26.1.2, 1.0.0-hotfix for 1.21.11, plus 1.20.1 and 1.21.1) carry a copy of this mod's v0.5 correction as a cancellable `@Inject(RETURN)` on `getPlayerHandPos` with no check for this mod. v0.5's own RETURN inject cancelled first, so only one correction applied; v0.6's first-person hook sits inside the method and can't pre-empt it, so EFL's copy would stack on the corrected origin (off the rod on windows other than 16:9, with FOV modifiers, while turning and crouching), and its rope, drawn by its own call from `lineOriginOffset`, would get neither the body-held offset nor the line hiding. User decision 2026-09-22: `breaks` on every branch, no EFL-specific code.

## Dev environment gotcha

Loom writes `.idea/runConfigurations/Minecraft_Client.xml` only when it is missing and never updates it, and `.idea` is shared by every branch of the checkout. A stale config on the 26.3 branch lacks `-XX:StackShadowPages=32` (from Mojang's version JSON), and the client then dies natively on an in-world resource reload (access violation in `jvm.dll`, no `hs_err`). A 26.x config on an old branch fails to start on JDK 21 (`--sun-misc-unsafe-memory-access`). After switching version families, delete the XML and run `./gradlew ideaSyncTask`.

## Versioning

Each Minecraft version lives on its own branch (e.g. `1.21.4`, `1.21.11`, `26.3`). The version numbers in `gradle.properties` (`minecraft_version`, `loader_version`, `loom_version` — on branches not yet ported to the current fix the Loom version sits in `build.gradle`'s `plugins` block instead — and `yarn_mappings` on pre-26 branches) must be updated together when porting to a new MC version. The `mod_version` in `gradle.properties` is independent of MC version.

## Roles

Project roles:

- `/port-version <mc_version>` — ports the mod (the current reference fix from the default branch) to a target Minecraft version, backport or forward-port. It reviews the port in rounds with `/reviewer` (correctness and performance per round, compatibility once in parallel) until no real bug is left, fixes the rest, and only then launches the game. See `.claude/skills/port-version/SKILL.md`.
- `/publish [branches|all] [notes]` — publishes release jars to CurseForge, then Modrinth. It first shows a player-facing changelog worked out from the code and commits and waits for approval, asks whether to change the main-page description, then shows one final summary (version names, changelog) for a last yes before uploading. Uploads go through `.claude/skills/publish/publish.py` (dry run unless `--send`). See `.claude/skills/publish/SKILL.md`.
- `/reviewer [scope] [--only <dimensions>] [notes]` — read-only, one-pass review of the branch's unpublished changes (or a range, paths, or `all`). Fresh reviewer agents check the default review, a performance gate (the mod's cost within noise of zero on a whole frame's budget) and compatibility with known mods, shader packs and resource packs; the findings are verified and returned as one report. It never edits, builds or commits. See `.claude/skills/reviewer/SKILL.md`.
